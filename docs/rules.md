# 開發規則

---

## 1. 程式碼所有權

**每個資料夾只有一個 owner，別人要動就開 PR。**

```
engine/  encoding/  harness/  serving/  submission.py   → A
agents/  model/  eval/                                  → B
contracts.py                                            → 凍結
```

原因：兩人改同一個 repo，衝突不是出在 git merge，是出在**同一個函式有兩個人在改它的行為**。

---

## 2. 測試三層

| 層 | 時間 | 內容 | 什麼時候跑 |
|---|---|---|---|
| **L0 smoke** | **< 60 秒** | 3 局固定種子，跑完整 720 回合 | **每次改動** |
| **L1 quick** | ~5 分鐘 | 30 局，看有沒有明顯變爛 | 想確認沒搞砸時 |
| **L2 判定** | 30~60 分鐘 | 統計判定是否真的變強 | 整合日、提交前 |

### 2.1 L0 檢查清單

**L0 不看勝率。** 3 局的勝率是純噪音，看了只會誤導。

L0 只回答一個問題：**有沒有壞掉、有沒有退步。**

```
□ 720 回合跑完，沒有例外
□ 零非法動作（全部通過 legal_mask）
□ 單回合最長耗時 < 時限的一半
□ 全程現金非負、庫存非負
□ 期末現金落在 baseline 容差範圍內
□ encode 出去再 decode 回來，結果一致
□ 模型檔的 ENCODER_VERSION 對得上
```

### 2.2 期末現金要跟誰比

❌ **不要寫 `final_cash > 0`。**

起始現金本來就大於零，一支從頭 `PASS` 到尾、什麼都不做的 AI 也會通過。**這條檢查是空的，抓不到任何東西。**

✅ **要跟 baseline 比。**

固定種子 + 固定對手 → 期末現金是一個**確定的數字**。存起來，之後每次改動都跟它比。

**Phase 1（規則式 AI，純 CPU）→ 用等號**

```python
assert final_cash == baseline[seed]
```

沒有網路、沒有 GPU、單執行緒 → 結果應該**每次都一模一樣**。

任何行為改變都會讓等號破掉。這是最強的回歸測試，連「我以為這次重構沒改到行為」都抓得到。

> 如果等號不穩定，那本身就是 bug：dict 迭代順序、`set` 的不確定性、沒固定的亂數種子。
> **去修它，不要放寬容差。** 這個「可重現」的性質後面會一直救你。

**Phase 2 之後（有網路 + 搜尋）→ 用範圍**

```python
assert 0.95 * baseline[seed] <= final_cash <= 1.20 * baseline[seed]
```

GPU 浮點運算的順序不完全固定，分數會有微小抖動，可能翻轉搜尋的排序。所以改成容差帶。

**上界也要有。** 現金暴增通常不是變強了，是規則鏡像算錯或繞過了合法性檢查。**三局 smoke 突然多賺 40%，該懷疑不是該慶祝。**

### 2.3 為什麼不是每次跑 200 局

因為那是把**測試**和**定論**搞混了。

改一行跑 200 局 → 一天只能迭代三次 → 專案死掉。

正解不是放棄統計驗證，是**用對的統計方法**：

**配對種子**

同一個種子、同一個對手，新舊兩版各跑一次，比的是**同一個局面下的差值**。

市場行情好不好、作物運氣好不好，這些共同的隨機因素直接抵消掉。**同樣的信心水準，需要的局數降到 1/3 以下。**

**SPRT（邊跑邊判定）**

不要固定跑 N 局，而是每跑完一局就算一次「證據夠不夠」：

```
假設 A：新版沒比較強
假設 B：新版強一點點

每局結束後更新證據強度
   夠強 → 判定「變強了」，停
   夠弱 → 判定「沒變強」，停
   還不確定 → 繼續（上限 400 局）
```

這是西洋棋引擎社群（Stockfish）調參的標準做法。

**實務效果：明顯的改動 30~50 局就判完了。** 只有真正邊緣的改動才會跑到上限——而那種情況本來就值得多跑。

L1 和 L2 是**同一套程式碼**，只是時間預算不同。

### 2.4 baseline 管理

- 存在 `tests/baselines.json`，**進版控**
- 只有在 L2 判定「確實變強」之後才更新
- 更新時把統計結果寫在同一個 commit 裡

> 🚨 **禁止「測試沒過就去調 baseline」。這是整套機制唯一的死法。**

## 3. Log 規格

**改東西就要加 log。而且要 log 判斷依據，不只是結果。**

### 分級

```python
LOG_LEVEL = 0   # submission 固定 0
# 0 = 完全安靜
# 1 = 每天一筆摘要
# 2 = 每回合一筆
# 3 = 決策細節（含搜尋過程）
```

### 每回合的格式

```json
{"t": 341, "day": 15, "cash": 8420, "crew": 3,
 "action": {"type": "HARVEST", "target": [4,7]},
 "chosen_score": 12.4,
 "top5": [["HARVEST", [4,7], 12.4],
          ["WATER",   [3,7], 11.9],
          ["PLANT",   [5,2], 10.1],
          ["NORTH",   null,   9.8],
          ["FEED",    [1,1],  9.2]],
 "search": {"nodes": 840, "depth": 6, "ms": 18.2},
 "invariants_ok": true}
```

> **`top5` 是整份 log 最重要的欄位。**
>
> 你要 debug 的不是「它做了什麼」，是「**它為什麼沒做那個更好的**」。
>
> 沒有候選清單和分數，你只能猜。

### 三條硬規則

**1. submission 的 `LOG_LEVEL` 必須是 0。**
Kaggle 對每步的 log 長度有截斷上限，而且字串格式化在 720 回合裡會實際吃掉時間。

**2. 不變式檢查永遠開著。**
現金非負、庫存非負、單位數合理。違反就記錄並拋錯。

成本極低，收益是**把靜默錯誤變成明確崩潰**。

**3. 每個 commit 附一份 L0 的 log 樣本。**
出事的時候你要能比對「上次正常的時候長什麼樣」。

## 4. 介面凍結

`contracts.py` 的三個函式簽名，**不准單方面改**。

### channel 順序規則

訓好的模型**綁死在 channel 順序上**。

```
✅ 只能往後加
❌ 不准調換順序
❌ 不准刪除
```

- 每次加 → `ENCODER_VERSION += 1`
- 存模型時把 version 寫進檔案
- **載入時版本不符 → 直接拋錯，不要嘗試相容**

### 要改介面的話

1. 兩人同時在場
2. 評估對現有所有模型的影響
3. 更新版本號
4. 重跑全套 L0 baseline

## 5. 證據規則

> **不能確定的事，不要用推論帶過。**

每個寫進程式碼的常數，只能是三種狀態之一：

```python
GROWTH_HOURS = {"wheat": 48}   # VERIFIED: interpreter.py 第 204 行
HIRE_COST    = 120             # UNVERIFIED — 從 replay 反推，見 unknowns.md #7
IRRIGATION_R = None            # UNKNOWN — 擋住 T11，owner: A
```

**規則：UNKNOWN 不准填猜測值繼續往下做。**

三選一：

1. 去原始碼查（通常幾分鐘）
2. 寫一支小程式跑 env 實測
3. 標成 UNVERIFIED 並登記進 `unknowns.md`

### 反面教材（這個專案真實發生過）

> 二手資料沒提到移動系統 → 推論「這遊戲沒有移動」 → 被遊戲畫面截圖打臉。

**「找不到證據」不等於「證據顯示不存在」。**

寫出「通常是」「往往」「一般來說」的時候，就是在說「我沒查」。看到這些字眼要停下來去查。

## 6. Git

- **`main` 永遠可提交。** 任何時刻 clone 下來都要能產出合法 submission。
- 一個改動一個 commit，message 註明跑過哪一層測試。
- 模型檔用 Git LFS 或外部儲存，**不要塞進 git**。
- 每個實際提交過的版本都打 tag：`sub-YYYYMMDD-genN`。
