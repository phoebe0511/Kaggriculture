## §128 植物鏈

### 128.0 WATER 與 PLANT 都沒到 1.0，但原因不同

§127.3 那張表裡 `WATER 0.998`、`PLANT 0.997`。**這兩個數字不能放在一起看：**

- **WATER 的 0.998 是量測方法的假數字**，§127.2 自己標了星號。兩個 unit 站同一格
  都送 WATER，回合開始時兩個都看到 `watered_today == False`、回合結束時兩個都看到
  `True`，`tools/op_waste.py:_did` 是比對格子狀態、分不出是誰做的，所以兩個都算成功。
  WATER **從來沒有進過 `turn_guard`** —— `git log -S turn_guard` 只有 ae90af8
  一個 commit，那個 diff 裡沒有 WATER；現在的 `contracts.py:1113` 也只對
  `PLANT_OP` 佔格。WATER 真正的白做工量在「同格重複」那一欄：**382 次 / 8 局
  = 47.8 次/局**。
- **PLANT 的 0.997 是修過之後真的殘留。** guard 有處理 PLANT，成功率
  0.766 -> 0.997，剩下那 0.3% 還沒有解釋。§128.1 是一個候選原因。

**這兩條都還沒結案，要繼續追。**

⚠️ **§130 把工具重寫之後這一節的數字全部改了**：WATER 是 0.904 不是 0.998，
PLANT 是 0.999 不是 0.997。下面 §128.1 ~ §128.4 的推論仍然成立（而且大多被
§130 證實），但只要引用到 §127.3 那張表的數字，都以 §130 為準。

### 128.1 🩸 `turn_guard_state` 的種子 avail 算多了

`contracts.py:1080` 的 docstring 寫：

> 可用量 = 回合開始時的存量 + 這回合 `BUY_SEED` 買的（**引擎先處理市場訂單**）

**括號裡那句是錯的。** 引擎 `interpreter` 的順序（行 894 起）：

```
行 935-938   _apply_unit_action(...)      逐 unit 執行；PLANT 在行 417-429 扣種子
行 941       _process_market(state, env)  ← 市場在 unit 動作「之後」
```

`docs/games/engine-notes.md:69` 的「引擎每回合的處理順序」本來就寫對了
（1. unit 動作 → 2. `_process_market`），是 `contracts.py` 的 docstring 跟它相反。

**所以這回合 `BUY_SEED` 買的種子，這回合種不了。**

而且引擎對 PLANT 有原子驗證（行 919-931）：

```python
seeds = s.observation.private.get("seeds", {})   # 回合開始的存量，不含這回合買的
blocked = {crop for crop, n in plant_demand.items() if n > seeds.get(crop, 0)}
```

某作物的 PLANT 請求數超過回合開始的種子數 -> **該作物這回合的所有 PLANT 全部變
`PASS`**，不是只擋多出來的那幾個（`engine-notes.md:394` 的第 9 條也記了這件事）。
所以 `avail` 高估 1 顆，可能一次損失好幾株。

修法：`turn_guard_state` 不要把 market 的 `BUY_SEED` 加進 `avail`，直接用
`obs["private"]["seeds"]`。

### 128.1.1 實測：`tools/seed_timing.py`

不是推論，是直接問引擎。四個 scripted agent 情境，手動 `env.step`，seed 900000。
測試環境沒有混淆：`private["seeds"]` 初始全部 0（引擎行 172）、farmer 生在 (4,4)
（行 159-164）、NW 象限已解鎖所以 (4,4) 是空地（行 157-158）。

```
情境                                       長出   種子餘額
T1  同回合 BUY_SEED WHEAT 1 + PLANT WHEAT    0 株   WHEAT 1   ← 種子留在手上
T2  控制組：step0 只買、step1 才種            1 株   —
T3  2 個 unit 站不同空地都 PLANT，只有 1 顆    0 株   WHEAT 1   ← 種子也沒被扣
T4  控制組：同樣 2 個 unit，買 2 顆            2 株   —
```

**T1 = 0 株：這回合買的種子，這回合種不了。** `contracts.py:1080` 的 docstring
確定是錯的，`turn_guard_state` 的 `avail` 高估。

**T3 = 0 株不是 1 株：原子驗證真的把該作物整批擋掉**，不是只擋多出來的那一個。
T3 連種子都沒扣（WHEAT 仍是 1），兩個 unit 那一回合什麼也沒做。

兩件事疊起來：`avail` 只要高估 1 顆，那一回合該作物的 PLANT **全部**作廢。

發生頻率在 §130 量到了：**8 局裡原子驗證只擋掉 2 次（MELON），0.2 次/局。**
機制是真的，但在實戰的量級很小 —— 不是 PLANT 白做的主因（PLANT 8 局只白做
1 次，而那 1 次的原因是「tile 已被佔（PASTURE）」，跨 op 同格，不是種子）。
還是要修（送出引擎會拒絕的動作不是策略選擇），但不要當成優先項。

### 128.4 佔格要跨 op，不是每個 op 各自一組

§127.3 有兩列的失敗數跟同格重複對不上：

```
op             發出   生效  失敗   同格重複(同一個 op)   對不上的
FERTILIZE       520    449    71          62                9
BUILD_COOP       30      1    29           2               27
```

`tools/op_waste.py` 的 dup 計的是 `(op, pos)` —— **只算同一個 op**。跨 op 的同格
衝突完全沒計到：

```
unit A HARVEST 非 ongoing 作物 -> 格子變 None -> unit B 的 WATER / FERTILIZE 落空
unit A PLANT                  -> 格子不是 None -> unit B 的 BUILD_* 落空
unit A DIG                    -> 格子變 None   -> unit B 的 WATER / HARVEST 落空
```

BUILD 是**免費**的（引擎行 493-503 沒有任何扣錢邏輯；`engine-notes.md:394` 第 6 條
也記了），所以 §127.4 第 3 條的 BUILD_COOP 0.033 不是錢的問題。跨 op 同格是目前
唯一的候選解釋，⚠️ 沒實測。

=> `claimed` 要做成**一格一個 unit，不分 op**。

⚠️ 還有一個要先排除的量測假影：`tools/op_waste.py` 拿 `step[t]` 的 unit 位置去查
`tiles[t-1]`。一般 op 不移動所以位置相同，但**每天早上農夫被重設到 (4,4)、hands
全部清空**（`engine-notes.md` §10.1、§10.2 / 引擎 `_end_of_day` 行 866-867），
日界那一步的位置對不上。24 步一次 = 4.2% 的步。BUILD_COOP 全表只有 30 個樣本，
這個假影足以污染它。

### 130.2 新版：掛在引擎上，不從 before/after 猜

包住引擎自己的兩個函式：

```
env.interpreter        每一步記下雙方送出的原始動作、自己算一次 PLANT 原子驗證，
                       並記下 farms 的 id 用來分辨玩家
_apply_unit_action     引擎逐 unit 執行動作的地方。在**單一次呼叫**的前後各抓一份
                       狀態（這個 unit 站的 tile、它自己的 inventory、shed、seeds），
                       所以是誰做成的完全確定
```

生效的判準不需要逐 op 寫規則：`_apply_unit_action` 對非法動作是靜默 return、
什麼都不碰（引擎行 313 docstring），所以「這一次呼叫有沒有改到任何狀態」就是
精確的判準。

🩸 **只有 FERTILIZE 要特判**：`_inv_take`（行 478）在 `max(...)`（行 481）之前，
同一天重複施肥「肥料扣掉了但沒有延長」—— inventory 有變，用通則會誤判成生效。
這個 op 只認 `fertilized_until_day` 有沒有變大。

⚠️ `kaggle_environments/core.py:625` 用 `self.interpreter.__code__.co_argcount`
決定傳幾個參數，所以 interpreter 的 wrapper 必須是 `def f(state, env)` 兩個位置
參數，不能寫 `*args`（argcount 會變成 0）。

欄位定義：
- **白做** = 發出 − 生效。這一欄是問題的大小，排序照它。
- **佔格造成** = 白做裡，那個 tile 這一回合已經被前面的 unit 佔走的部分

  把 `turn_guard` 擴充成「任何 tile 專屬的 op 都佔格」之後，消掉的就是這些。
- **%** = 佔格造成 / 白做。**這一列改 `turn_guard` 有沒有用、有多少用。**
  100% 代表全部是同回合撞車、改了就歸零；0%（PICKUP）代表改了完全沒用，
  要從別的地方修。**合計 2,061 / 2,161 = 95%。**

餵完再收，兩個都成立），混在白做裡會讀錯。要看的是「白做」和「佔格造成」。

    動作前的重選**。引擎原始碼裡 `if tile is not None: return` 那類檢查也叫
    guard（`engine-notes.md:112` 的「LOCKED guard」，引擎原始碼的原詞），
    是引擎的，兩者不是同一件事 —— 表上不要用裸的「guard」當欄名。
  - 這個東西的名字是 **tile**，不是「格子」。`engine-notes.md:109/115/160`
    和 §127.4 都寫 tile。
  - 引擎對非法動作的行為叫 **靜默 no-op**（引擎行 313 的 docstring
    `Invalid / illegal actions are silent no-ops`，`engine-notes.md:67` 已有
    中譯寫法），不要叫「早退」。

### 130.6 🩸 FERTILIZE 是唯一 guard 修不掉一大半的

```
FERTILIZE 白做 148   其中已佔格 90（61%）   剩下 58 不是已佔格
```

`fertilized_until_day = max(舊值, day + 2)` 覆蓋 day / day+1 / day+2 三天。
所以**同一天的不同回合**對同一格施第二次肥，也是扣了肥料、沒有延長。
`turn_guard` 只管單一回合，管不到跨回合。

但這個**不需要 guard，mask 就擋得掉** —— `fertilized_until_day` 在 tile 狀態裡
看得到。`contracts.py:939` 現在是：

```python
elif op == "FERTILIZE":
    mask[i, j] = kind == "PLANT" and inv.get("FERTILIZER", 0) > 0
```

要加的條件是 `tile.get("fertilized_until_day", -1) < day + 2`。

⚠️ 沒有實測這一條會擋掉多少 —— 上面的 58 是「同一天、不同回合」的下界估計
（148 − 90，假設已佔格那 90 次全部發生在同一回合，這是定義上成立的）。

## §131 turn_guard 改寫：`claimed` 位置黑名單 -> tile 狀態模擬

無條件生效，沒有旗標（§125.5 那條線）。

### 131.1 為什麼不是把 `claimed` 擴充就好

原本打算把 `claimed` 從「只有 PLANT 佔格」改成「任何 tile 專屬的 op 都佔格」。
先量了一下會誤擋多少 —— `tools/op_waste.py` 加了「已佔格但照樣生效」的配對統計：

```
共 390 次（8 局）會被誤擋
  102  COLLECT_FERTILIZER -> CARE     同一隻動物，收完肥料再照顧，兩個都成立
   63  FEED -> COLLECT_FERTILIZER
   48  FEED -> HARVEST                先餵再收蛋
   38  COLLECT_FERTILIZER -> FEED
   34  FEED -> CARE
   30  HARVEST -> COLLECT_FERTILIZER
    7  WATER -> FERTILIZE
```

🩸 **`claimed` 只有一個 bit：「這個 tile 有人動過」。** PLANT 的合法性剛好就是
`tile is None` 一個 bit，所以當初夠用。但同一個作物 tile 上 `watered_today` 和
`fertilized_until_day` 是兩件獨立的事，同一個動物 tile 上 `fed_today` /
`cared_today` / `fertilizer_available` / `yield_units` 是四件獨立的事 ——
一個 bit 蓋不住。

### 131.2 改成模擬 tile 狀態

`turn_guard_state(obs)` 回傳 `{tiles, seeds, day}`：

```
tiles   每格的狀態，複製一份。WATER 寫 watered_today、HARVEST 清 yield_units、
        DIG 清成 None…… 後面的 unit 照這份判，不照 obs 那份
        （copy-on-write：改到哪一格才複製那一格的 dict，不動到 obs）
seeds   全農場共用的種子存量
```

不記的兩樣，各有明確理由：

```
每個 unit 自己的 inventory   一個 unit 一回合只做一個動作，它自己的 inventory
                            在它動之前不會被自己改，別的 unit 也碰不到。所以
                            legal_unit_mask 算出來的 inventory 條件不會過期。
「這一格有沒有別的 unit」     引擎完全不看。_apply_unit_action（行 312-530）從頭
                            到尾只讀自己那個 unit 的位置和 inventory，沒有任何
                            一行看別的 unit 在哪 —— unit 重疊完全合法。
                            而且 tile 狀態嚴格包含「有沒有人動過」且更精確。
```

`_guard_ok(op, arg, state, pos)` 逐條對應引擎的 early return（行號寫在 code 的
註解裡）；`_guard_apply` 把效果套回 `state`。`contracts.py:65` 本來就直接從引擎
import `CROPS` / `ANIMALS`，所以 `ongoing` / `first_yield_day` 這些不會跟引擎漂掉。

🩸 順帶把 §128.1 修掉：`turn_guard_state` 不再吃 `market_orders`。引擎的
`_process_market`（行 941）在 unit 動作（行 935-938）**之後**，這回合買的種子這
回合種不了（§128.1.1 實測）。兩個呼叫端的簽章跟著改。

⚠️ PICKUP / PLACE / DROP **刻意沒納入**。shed 也是全農場共用一份，PICKUP 撞車
確實會白做，但搬運量由 qty head 決定、`turn_guard` 拿不到 qty，模型會不準；
而且 DROP 會在同一回合把東西加回 shed。寧可不管也不要亂擋。

### 131.4 §128.2 / §130.6 不用改 mask 了

`_guard_ok` 對**每一個** guard op 都重查一次，不是只查「tile 被動過」的那些。
所以 HARVEST 的 `first_yield_day`（§128.2）和 FERTILIZE 的「同一天已經施過」
（§130.6）自然包含在裡面 —— 這兩條本來要改 `legal_unit_mask`，現在不必。
上表 HARVEST 和 FERTILIZE 都到 1.000 就是它。

⚠️ 但**還有一個沒解的**：mask 沒改，代表 policy 仍然**會選**這些動作，只是被
guard 換掉（訓練側標 `op_exec=False`）。要不要把條件也放進 mask 讓 policy 根本
選不到，是 learning signal 的問題，不是規則正確性的問題 —— 跟
`legal_target_mask` 那條「寧可放寬，絕不擋掉老師去過的格子」的不變式有張力，
還沒決定。

### 方法上的四條

```
1  🩸 量「引擎有沒有執行這個 unit 的動作」不要比對回合前後的盤面 —— 同 tile
   互斥的 op 會讓兩個 unit 都被算成成功。掛在 _apply_unit_action 上，單一次
   呼叫的前後各抓一份，歸屬才是確定的。
2  kaggle_environments 的 env.interpreter 是 instance attribute（core.py:232），
   可以直接換掉。但 core.py:625 用 __code__.co_argcount 決定傳幾個參數，
   wrapper 要寫成 def f(state, env)，不能用 *args。
3  🩸 要擋「同回合衝突」不要用位置黑名單 —— 一個 tile 上有好幾個獨立的每日
   旗標，一個 bit 蓋不住，會誤擋（實測 390 次 / 8 局）。模擬 tile 狀態。
4  用詞：tile（不是「格子」）、靜默 no-op（不是「早退」）、佔格 / claimed。
   turn_guard 是我方送出動作前的重選；引擎自己那些 early return 也叫 guard，
   兩者不是同一件事。
```

⚠️ 規則正確性**不要用 margin 判**（§125.5）。n=20 的 margin SE 是 4,773，
光換 seed 就能造出 +2,131 的差（§120）。
