## §68 第二輪 CMA-ES：130 代收工，候選全面贏過 `cma1-g50-wt`

### 68.1 這一輪跑了什麼

```

python -u -m tools.param_search --warm-start config/params/cma1-g50-wt.json \
    --seeds 40 --popsize 15 --generations 243 --checkpoint-every 10 --workers 10

40 維全搜（不是 --only 子空間）。跑 130 代放 STOP 收工，sigma 0.0254。
存檔完整，--resume temp/cma/20260901-174022 接得回去。
```

先開了 14 維聚焦那輪（`--only s65`），25 分鐘就停掉 —— 停的理由是**凍住 26 維
等於假設「那 26 維的最佳值不會因為那 14 維動了而跟著移」，而這件事沒有任何
測量支持**。詳見 §66.5。

### 68.3 停下來的理由

不是「開始變差」（holdout 最後兩個 checkpoint 是歷來最高的兩個），是
**用 40 局判不動，再跑 14 小時還是用 40 局判不動**：

```
holdout 40 局    SE 4,092    ← 搜尋期間唯一的誠實數字
驗收 400 局      SE   567
```

sigma 也已經收到 0.0254，而 2026-08-25 量到 margin 在 sigma≈0.05 時要 54 個
seed 才排得動相鄰候選，我們只有 40 個。

### 68.5 gen1 那個零怎麼解釋

搜尋過程中 `gen1` 那一欄一直不漲（八支重播平均漲到 +11,810，gen1 十次量測
平均約 0），一度懷疑是**學到專打不會反應的重播**（`param_search.py` 的註解
就寫著這個風險）。

排開四種對手之後這個懷疑不成立：

```
對手              會反應   強度    候選比出貨版好多少
ladder-top-a        ✗      強      +15,449   t=+9.74
另外八支重播        ✗      強      +11,810   （checkpoint）
cma1-g50-wt         ✓      強       +6,731   t=+11.88   ← 關鍵
gen1                ✓      弱          ~0
```

**「會反應」那條軸有覆蓋了，候選照樣贏。** 剩下的解釋是 gen1 太弱：對它我們
已經賺到 100,106（比對誰都高），市場吃滿，再有效率也沒地方賣。

⚠️ **誠實剩下的限制**：會反應的證據**全部來自我們自己的程式碼血統**
（`cma1-g50-wt` 和 `gen1` 都是 gen0）。真人的 replay 一律不會反應，所以
「強 + 會反應 + 不是我們自己」這個組合量不到。而「贏過自己舊版」這把尺
騙過一次（本機對 gen1 100 勝 0 負、線上排 3000/5000）—— 但這次它不是唯一
證據，同一組參數對**八個不同真人的重播**也全面變好。

## §71 day 0 的空地：填得起來，填了更窮

§69 量到最大的缺口在開局（day 0 空地率我們 52%、對手 8%）。查了控制它的
參數 `seed_backlog`，結論是**這條不用再試了**。

### 71.1 旋鈕有效，缺口填得起來

一局 smoke（seed 2000，對 `ladder-top-a`，只改 `seed_backlog`）：

```
                     day 0    day 2    day 5    我方期末現金
backlog 0.225（現況）  7 格     10 格    18 格      95,151
backlog 1.0          16 格     18 格    18 格      72,698
backlog 1.5          18 格     18 格    18 格      69,662
```

day 0 從 7 格拉到 18 格（對手 19 格），**缺口完全填得起來**。
但我方期末現金掉兩萬多。

### 71.2 三份獨立證據都指同一邊

```
2026-08-28   單獨 A/B（0.5 / 1.0 / 1.5）三版都輸
第二輪 CMA-ES  聯合搜尋停在 0.2247 —— 那個值在算式裡等於沒開
今天 smoke     一局，填滿 day 0，我方現金 -22,453
```

⚠️ **不要說「CMA-ES 沒測過它」。** 第二輪 `sigma0` 0.2（正規化）= 實際值
0.3，起點 0，所以 1.0 以上約 3 個 sigma —— 1,950 個候選裡估計抽到十幾次，
**抽到過，沒贏過**。（這是估算，不是逐候選數出來的。）

第三輪不同：`sigma0` 0.05、起點 0.225，跳到 1.0 要 15 個 sigma，
**第三輪確實不會抽到**。要讓它再被搜到得換 sigma 或換界線。

### 71.3 🩸 這條算式有一半是平的

```
target = max(流量目標, int(等著種的格數 × 該作物佔比 × seed_backlog + 0.5))
```

day 0 的典型值（13 格空、4 種作物、CARROT 週期 4 天、`seed_buffer_days` 3）：
流量目標是 2，而 backlog 項要到 `seed_backlog >= 0.769` 才算得出 3。

**所以 [0, 0.769) 這一段（搜尋範圍的 51%）行為逐位元組相同。** CMA-ES 在那
一段拿到零訊號，值只會隨機漂 —— 停在 0.2247 不代表 0.2247 比 0.5 好。
`int()` 加 `max()` 造成的，不是遊戲本身的性質。

### 71.4 這把問題翻過來了

原本的推論是「我們 day 0 只種 7 格、對手種 19 格，所以輸」。現在知道
**我們種得到 18 格，種了反而更窮**。跟 §64.5 記的一致（128 局 ladder：
作物格數愈多勝率愈低，26% -> 7%，r = -0.193）。

所以缺口不在「種幾格」。剩下兩個沒查過的方向：

```
□ 對手 day 0 種的是哪幾種作物、幾天後第一次變現
  （推測他們種小麥、first_yield_day 2 就變現，我們的組合回收慢）
  ← 從 replay 撈得到，不用跑對局
□ day 0 那筆錢不種地的話該拿去做什麼（買動物？雇人？）
```

⚠️ 上面兩條都是推測，沒量過。
