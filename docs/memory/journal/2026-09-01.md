### 57.3 gamma=1.0：value head 修好了，成績沒動

`--gamma 1.0 --lam 0.998`，其餘照 `ab-lam`。**34 個 checkpoint 從來沒有
一支設過 `--gamma`**，全部吃預設 0.997。

動機（實算）：`0.997^240 = 0.486`、`0.997^718 = 0.116`。reward 是
`(da-db)/10000`，**不打折相加會 telescope 成期末現金差** —— 也就是真正的
目標。加 gamma=0.997 之後，「第 0 天花 1 塊、第 10 天收回 1.5 塊」在訓練
目標裡算成 `-1 + 1.5×0.486 = -0.27`，是虧的。**要回收 2.06 倍才不虧。**

結果：40 局差額 −24,849，跟未訓練的 −24,952 分不出來。

**但 value head 確實修好了**（§58.2 的真 MC 量測）：對實際終局結果的
解釋力 0.416，`ab-lam` 只有 0.064。**它學會判斷盤面了，成績還是沒動 ——
所以 credit assignment 不是瓶頸。**

## §60 兩次改動都失敗，各自的原因

### 60.1 `per_crop_lookahead` —— 實作了，變差，而且前提本來就錯

## §61 🔴 PPO 看不到對手種什麼

`contracts.py` 的觀測編碼，關於對手只有：

## §63 🔴 策略結論：手動調 CMA-ES 搜過的參數，期望值是負的

使用者問的：「我們不是做了 CMA-ES 調過參數了嗎？所以再調是可以比 CMA-ES 調得好嗎」
**答案是不能，而且今天的四次失敗就是證據。**


CMA-ES 把 53 個參數（實際搜 34 個連續的）當**一個向量**最佳化。單獨動一維
就是從最佳點往一個方向走一步，而參數互相牽動，那一步幾乎必然變差。

🩸 **我今天犯了更基本的錯**：加了 `per_crop_lookahead` 這個新開關，
然後用「CMA-ES 在沒有這個開關的前提下調出來的 53 個值」去測它。
**那必然失敗**，跟開關本身好不好無關。

### 63.1 唯一成功過的那次，不是調數值

```
2026-08-28  whole_turn_assignment  +7.0pp  z=2.99  ✅
```

那是**換掉派工演算法**（「照優先序一層一層發」→「一次全域最短配對」）。
CMA-ES 只能在舊演算法內部調數字，**結構上搜不到那個行為**。

分界線：

```
參數空間裡調數值        CMA-ES 已經搜過      → 不要碰
參數空間表達不出來的     CMA-ES 搜不到        → 這裡才有空間
```

今天修的補位 bug（§60.2）也屬於後者 —— 那不是調參數，是把一個
「`crop_share` 講不出來的東西」變成講得出來。

# §66 §65 執行了：搜尋空間 34 -> 40 維，聚焦重搜開跑

## 66.1 做了什麼

三個新旋鈕進 `tools/param_space.py` 的 `SEARCH_SPACE`：

```
structure_spread   [0.0, 1.0]   建物散到幾個象限。0 = 現在的 12/0/0
seed_backlog       [0.0, 1.5]   等著種的格數要先買齊幾成的種子。0 = 現在
crop_share × 5     [0.0, 1.0]   逐作物的格數上限，取代全域 max_crop_share
```

`crop_share` 是 dict，整包塞不進連續空間。做法是**帶點的 key**
（`"crop_share.WHEAT"`），`encode` / `decode` 認得那個點。**`agents/gen0.py`
一行都沒改** —— decode 出來還是同一個 dict，只是五種作物全列出來了。
「沒列到的作物走哪個值」由 `DICT_FALLBACK` 宣告，抄的是 `gen0` 既有的
`share.get(c, max_share)`。

`max_crop_share` **移出搜尋空間**：五種全列出來之後 `share.get(c, max_share)`
永遠命中，它在 `_greedy_basket` 就再也讀不到。留著會是一個對目標函數零影響的
維度。（短局實測確認：展開之後把它從 0.2874 改成 0.4，期末現金一毛不變。）

`structure_spread` / `seed_backlog` 原本刻意不進 `DEFAULT_PARAMS`，現在進了 ——
`_check_space` 要求 `SEARCH_SPACE` 的 key 必須在 `DEFAULT_PARAMS` 裡。
`tests/test_frozen_reference.py` 的 `_ADDED_AFTER_REF_V11` 白名單從 tuple 改成
dict（key -> 不改變行為的值），ref-v11 的 sha256 不受影響。

## 66.2 🩸 途中量到一個會安靜吃掉整輪成果的洞

`decode()` 是從 `DEFAULT_PARAMS` 重建的。而 `config/params/cma1-g50-wt.json`
有**兩個不在 `DEFAULT_PARAMS` 裡**的 key：

```
whole_turn_assignment: True    2026-08-28 的 +7pp，這個專案唯一成功的改動
priority_step_cost:    1
```

它們用 `params.get()` 讀，所以不在預設表裡也生效；不放進預設表是因為那會改掉
`gen1` / `ref-v11` 這些對手的行為。

結果：`--warm-start config/params/cma1-g50-wt.json` 只取 x 的話，這兩個 key 在
`decode` 時直接消失 —— **整輪 CMA-ES 會在搜一個沒有那個 +7pp 演算法的 agent**，
而且分數只會低一截、不會報錯。短局自我對戰實測 4,910 -> 4,756。

修法：`decode(x, base=None)`，暖啟動時 base 是那份 config 的完整 params。
`tests/test_param_space.py::test_decode_without_base_drops_keys_that_predefaults_does_not_have`
釘住這件事。

**這個洞是被新寫的「展開前後行為必須相同」那條測試抓到的**，不是想出來的。

## 66.3 `--only` 子空間

```
python -m tools.param_search --warm-start config/params/cma1-g50-wt.json --only s65 ...
```

CMA-ES 只看見 `s65` 那 14 維，其餘 26 維留在起點。存檔多三個欄位
（`active_keys` / `x_base` / `base_params`），`--resume` 靠它們展開回去。

`s65` 的收錄標準只有一條：**跟新加的維度搶同一個稀缺資源，或直接夾住它**。

```
新的 7 維     crop_share × 5、structure_spread、seed_backlog
開局現金      seed_buffer_days、animal_spend_frac
unit-turns    max_hands、hands_per_quadrant、tiles_per_unit
作物上限      oversupply_factor、n_structures
```

🩸 `max_hands` 和 `hands_per_quadrant` **兩個都要進**：
`land_cap = min(max_hands, hands_per_quadrant × 已解鎖象限)`，出貨值是 11 / 4 /
最多 3 象限 —— 前期 1 個象限時由 `hands_per_quadrant` 夾成 4 人、後期由
`max_hands` 夾成 11 人。凍任何一個都會鎖死半局的人數。

刻意不收：`cash_reserve_days`（出貨值 0，已經全關）、`animal_reserve`（跟
`animal_spend_frac` 管同一筆錢）、`land_first_min_day`（買地時機是另一條軸）。

## 66.4 🩸 加了「第 0 代」—— 起點自己的分數

CMA-ES **只評估取樣出來的候選，平均值本身從來沒被評估過**。所以「歷來最佳」
是候選之間的比較，跟起點無關 —— 整輪跑完的最佳解**可能比起點還差**，而舊的
log 裡沒有任何一欄看得出來。

現在新開一輪會先把起點跑一次 train + holdout + 九支隊伍，寫成 `checkpoints.jsonl`
的第 0 代，`--watch` 印成一條線：

```
起點（暖啟動的那組參數）    -14,227   ——   還沒超過起點
🩸 歷來最佳還低於起點 —— 現在收工的話應該維持原本的出貨版
```

`--watch` 的「動最多的參數」也改了排序：從「相對變化」改成「走了搜尋範圍的
幾成」。舊的除以起點值，而起點是 0 的維度被 `and v0` 整個跳過 ——
`structure_spread` / `seed_backlog` 這兩個**正是這一輪要看的**維度永遠不會
出現在表上。

## 66.5 先開了 14 維聚焦，然後改成 40 維全搜

14 維那輪（`temp/cma/20260901-173346`）開了約 25 分鐘,第 0 代基準線剛跑完就
停掉了,沒有跑完任何一代。**停掉的理由是設計上的質疑,不是它壞了。**

質疑:凍住 26 維等於假設「那 26 維的最佳值不會因為那 14 維動了而跟著移」,
而這件事**沒有任何測量支持** —— 我是照「搶同一筆開局現金 / 同一批 unit-turn /
同一批格子」挑的,那是推理。

聚焦的兩個真實優勢(不是速度):

```
covariance 的自由項   40 維 d(d+1)/2 = 820
                      14 維             105
```

CMA-ES 學「哪幾個參數要一起動」就是靠這個矩陣,它要從每代 12~15 個樣本估出來。
所以「維度愈多愈能捕捉環環相扣」不成立,反過來才對:維度愈多,估出來之前的
排序都是在猜。另一個優勢是**可以過擬合的自由度比較少** —— 上一輪的失敗模式
正是過擬合(出貨的是第 50 代不是第 68 代)。

但對我自己不利的事實是:**上一輪就是 34 維全搜,跑了 108 代,而且成功了**
(現在的出貨版就是它)。所以全維度在這個問題上可行,不是做不到。

決定:**跑 40 維全搜。**

## 66.6 這一輪在跑什麼


```
temp/cma/20260901-174022
指令  python -u -m tools.param_search --warm-start config/params/cma1-g50-wt.json \
        --seeds 40 --popsize 15 --generations 243 \
        --checkpoint-every 10 --workers 10
```

沒有 `--only`,40 維全開。起點仍是 `cma1-g50-wt`(所以那兩個不在
`DEFAULT_PARAMS` 的 key 有帶進去 —— 開頭那行會印出來確認)。
popsize 15 = CMA 對 40 維的預設 `4 + 3·ln(40)`。

🩸 `python -u`。沒有 `-u` 的話 stdout 是塊狀緩衝,行程被硬殺時 traceback
會留在緩衝區裡丟掉。

⚠️ **`--seeds` 用 40，不是 §65 寫的 20。** 理由是 2026-08-25 量到的噪音：
margin 在 sigma=0.05 時要 54 個 seed 才排得動相鄰候選，而上一輪的收工診斷就是
「sigma 已經小到 20 個 seed 排不動」。代價是一代 480 局而不是 240 局。

估時（今天實測吞吐 5,499 局/小時、10 workers）：一代 600 局約 6.5 分鐘，
243 代約 26.5 小時，加上 24 次 checkpoint（各 220 局）約 1 小時 —— 共約 27.5
小時。

看進度：

```
python -m tools.param_search --watch temp/cma/20260901-174022
```

要停：在那個目錄放一個 `STOP` 檔，當代跑完會乾淨收工（存檔完整，可以 `--resume`）。

⚠️ 驗收看 `checkpoints.jsonl`，**不要看 `best.json`** —— 上次跑 108 代，出貨的
是第 50 代不是第 68 代。而且這次多了第 0 代那條線：holdout 沒有明顯高過第 0 代
就不要換出貨版。
