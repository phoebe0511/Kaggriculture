## 1. 要解決什麼

2026-08-24 量到模仿這條路已經接近天花板（journal `2026-08-24.md` §1/§2）：

    round6 對 gen1 的現金比          93%    模仿得夠像了
    gen1 對 ladder-top-a 的現金比    56.8%  被模仿的對象只有這樣
    round6 對 ladder-top-a           50.7%

**模仿架構的上限就是被模仿的對象。** 就算 round7 模仿到完美，終點是 `gen1`
的 64,030，而 `ladder-top-a` 是 112,719。缺口 45% 不在網路，在 expert。

同一天量到的三件事排除了其他選項：

| 做過的嘗試 | 結果 |
|---|---|
| 再加 200 局 DAgger 資料 | p=0.599，判不出差別 |
| 加大模型（96/6 → 128/8） | 有效（84% → 93%），但驗證指標已平，到頂 |

## 3. 演算法：CMA-ES

### 為什麼

1. **它學參數之間的相關性。** covariance matrix 就是在描述「A 往下調的時候
   B 要跟著動」。2026-08-24 的買地實驗（單獨改一個參數 −58%）直接證明這個
   問題的參數是互相咬合的，座標下降 / 逐參數掃描會系統性踩坑。
2. **34 維落在適用區間**（CMA-ES 通常用在 10~100 維）。
3. **population-based，對評估噪音有一定容忍度** —— 我們的評估必然是吵的。
4. 不需要梯度，只要能評分。

### 為什麼不是別的

- **貝式最佳化（GP-based）**：強項是「評估極貴、維度低（<20）」。51 維對 GP
  是災難，除非先大幅降維。
- **座標下降 / 逐參數掃描**：見上面第 1 點。
- **`scipy.optimize.differential_evolution`**：可以當備案（scipy 1.17.1 已裝），
  也是 population-based、處理混合型參數，但不學 covariance，收斂通常比 CMA-ES 慢。

### 相依套件

`cma` **還沒裝**（`pip install cma`）。scipy 1.17.1 / numpy 2.2.4 已在環境裡。

## 4. 先做這一步：量噪音（半小時）

**這一步的結果決定整件事可不可行，沒做完不要進 §5。**

CMA-ES 每次評估要跑幾局，取決於相鄰參數點之間的評估噪音有多小。

目前手上唯一的噪音數字是 **配對差 sd = 15,435**，但那是拿 round6 和 `gen1` 比
出來的 —— 兩個策略完全不同、軌跡整局發散。BBO 比較的是**相鄰**參數點，改動小、
軌跡發散也小，噪音**應該**低得多。低多少沒人量過。

### 做法

挑一個小幅參數改動（建議 `cash_reserve_days: 3 → 2`，理由是它只改現金底線、
不改策略骨架），對 `ladder-top-a` 跑 100 局配對，算配對差的 sd：

```powershell
# 建 config/opponents/gen1-reserve2.json，params: {"cash_reserve_days": 2}
Remove-Item Env:KAGGRI_WEIGHTS -ErrorAction SilentlyContinue
python -m eval.runner --a gen1-reserve2 --b ladder-top-a --games 50 --workers 16
python -m eval.runner --a gen1         --b ladder-top-a --games 50 --workers 16
# 然後逐局配對（同 seed、同 a_slot）算 sd
```

### 判讀

| 配對差 sd | 每次評估要幾局 | 結論 |
|---|---|---|
| ~3,000 | 20~30 | CMA-ES 一兩個晚上跑得完，值得做 |
| ~8,000 | 100+ | 貴四倍，先降維（§6）再說 |
| 15,000+ | 400+ | 太貴，要換更便宜的評估方式（§6） |

## 5. 如果噪音夠小：CMA-ES 的設定

### 搜尋空間（51 個 key 拆三類）

| 型別 | 數量 | 處理 |
|---|---|---|
| `int` | 21 | 連續搜尋 + `round()` |
| `float` | 13 | 直接搜 |
| `bool` | 11 | 連續 [0,1] + 閾值 0.5（會產生平台區，梯度資訊差） |
| `tuple` | 2 | `basket`、`late_crew_caps` — **凍結不動** |
| `str` | 2 | `fallback_crop`、`animal` — 類別型，**凍結**或事後窮舉 |
| `dict` | 2 | **凍結** |

→ **34 維進 CMA-ES（21 int + 13 float），11 個 bool 用閾值，6 個凍結。**

起點用 `DEFAULT_PARAMS`（已經人手調過，是個好的 x0）。每個參數要給合理的
上下界，不然會搜到不合法的組合（例如負的 `max_hands`）。

### 目標函數

對 `ladder-top-a` 的平均期末現金，固定 seed 集合（common random numbers）。

🩸 **每次評估必須用同一組 seed**，否則不同候選的分數不可比，噪音會爆炸。

⚠️ 只用 `ladder-top-a` 有 overfit 到單一對手的風險。`ladder-top-b` 也在
`config/opponents/`，考慮混合池。但混合池會讓每次評估更貴，要權衡。

### 成本

```
34 維  ->  population 14  ->  經驗法則 100×dim = 3,400 次評估 = 243 代
每代：14 候選 × 20 局 = 280 局 × 31.49 秒 / 16 workers = 9.2 分鐘
243 代 ≈ 37 小時
```

（31.49 秒/局是 2026-08-24 實測 `gen1` vs `ladder-top-a` 的單局時間。
`gen0` 自我對戰只要 7.79 秒/局，但那是自我對戰，跟 ladder 表現的相關性沒驗過。）

### 分次跑與多機

- **可以分次。** CMA-ES 的狀態（mean / covariance / sigma / 代數）約 10 KB，
  每代結束 pickle 存檔，下次載入續跑。
- **同一代內可以拆到不同機器**（14 個候選互不依賴）。
- **代與代之間不能平行** —— 下一代的分布由上一代的結果決定。
- 🩸 **多機的前提是引擎版本完全一致**（`kaggle-environments==1.32.7`）。
  `docs/CLAUDE.md` 記著「本機引擎原始碼被人手改過」（`LAND_ORDER` 曾被改成
  `["NE"]`）。不同機器的引擎不一致的話，最佳化會學到錯的東西而且不會報錯。
  **開跑前每台機器都要對一次引擎檔案的 hash。**

```python
es = cma.CMAEvolutionStrategy(x0, sigma0, {"bounds": [lo, hi], "popsize": 14})
while not es.stop():
    X = es.ask()
    f = [-evaluate(x) for x in X]      # CMA-ES 是最小化，現金要取負
    es.tell(X, f)
    pickle.dump(es, open("cma_state.pkl", "wb"))
```

   ⚠️ 但那跟 ladder 表現的相關性**沒驗過**，要先量相關係數，不然是在最佳化
   一個跟目標無關的東西。
3. **CMA-ES 的 noise handling**（UH-CMA-ES，重複評估不確定的候選）。

## 7. 風險與已知的限制

- **產出的還是規則式。** BBO 最好的結果是「更強的 `gen0`」。要讓網路版受益
  還要 DAgger 模仿一次，而現在的還原度是 93% —— **收益要先乘 0.93。**
- **`ladder-top-a` 是開迴路重播。** 我們一下場市場價格就跟原局不同，它的
  `BUY_*` / `HIRE` 可能失敗，農場會逐漸偏離原軌跡（`agents/replay.py` docstring）。
  它是目前最好的量尺，但不是真實對手。
- **overfit 到單一對手**：見 §5 目標函數那段。
- ⚠️ **凍結量尺會位移。** `ref-v3`…`ref-v11` 各有 19 個 key 沒展開，會
  fall through 到 `gen0.DEFAULT_PARAMS`。**BBO 找到的新參數如果寫回
  `DEFAULT_PARAMS`，所有凍結尺會同時位移而且不會報錯。**
  新參數要用新的 config JSON（完整展開 51 項），不要改 `DEFAULT_PARAMS`。
- **這算不算偏離路線圖**：`docs/CLAUDE.md` 的方法路線寫的是
  「規則式暖身 → 訓練網路 → 網路 + search → 再訓練」。把力氣花在最佳化
  `gen0` 的參數上，是抬高 expert 而不是做 search。**這個判斷需要人決定。**
