⚠️ **接手的人先看 §1。** 昨天的 v5（`gen4_demand`）不是「網路版」，它是
`gen0.py` 換一個包裝，而且**包得比原版差 4.4%**。今天把路線改掉了。

## 1. 定調的那個數字

```
40 局配對   gen4_rulemarket(v5 網路)  88,483   vs   gen1(純規則)  92,597
```

**網路的加值是負的。** v5 只讓網路輸出一張 `[11,100]` 的 bool（哪一格要做
什麼）；配對（`_minimum_cost_assignment`）、走路（`step_toward`）、`FETCH_*`
趟數、`PLANT` 種什麼、整個市場（`_market`，269 行）全部是 gen0 原封不動。

三代網路（v3 逐 unit target、v4 市場、v5 逐格 demand）全部是模仿，而
**模仿的天花板就是被模仿的對象**。

### 兩個框架上的更正（我昨天講錯的）

1. **「DAgger 天花板是 gen1」≠「這條路走不通」。** `docs/CLAUDE.md` 的路線是
   Expert Iteration：規則式 → 訓練網路 → 網路 + search → 再訓練。
   DAgger + gen1 expert **就是「訓練網路」那一步**，目的不是贏 gen1，是產出
   prior 和 value head 讓 search 有東西可站。「重現 gen1 的 95.5%」是這一步
   該有的結果。
2. **不能拿 88,483 當新架構的門檻** —— 那是 gen0 的成績，不是網路的。
   正確的基準是規則式自己（榜上 7 萬+、本機配對 92,860）。

## 2. 新路線：端到端 prior

**search 只搜得到網路輸出的東西。** v5 的 demand map 表達不了市場、表達不了
配對，所以 search 永遠碰不到那兩塊。prior 必須是完整動作空間：
44 個 `UNIT_OPS` + 21 個 `MARKET_OPS`。

驗收標準跟 v3/v4/v5 完全不同：

| 階段 | 看什麼 | 不看什麼 |
|---|---|---|
| 1. 模仿 | **top-k 涵蓋率**、value RMSE | argmax 準確率、勝率 |
| 2. search | search 對規則式的 40 局配對勝率 | 網路自己的準確率 |
| 3. 重訓 | 對規則式的配對勝率 | — |

search 要的是「正確答案在候選裡」，不是「第一名就對」。而這個 repo 已經量過
**三次**「準確率不預測實戰」（08-19 §7d、08-20 §7、08-20 §11）。

## 4. 合併 gen0 / gen1

`agents/gen1.py` 97 行 = 21 個 key 的 `DEFAULT_PARAMS` + `act()` 直接呼叫
`gen0_act`。它存在的理由寫在自己 docstring（「Gen0 保持為 ref-v2 的凍結量尺」），
而 ref-v2 的參數本來就寫在 JSON 裡 —— 理由不成立，歷史遺留。

### 🩸 差點踩到的坑：檢查方向搞反

第一次我檢查「哪些 **gen0** 的 key 沒被 config 展開」，得到 5 個，就下結論
「合併安全」。**該查的是哪些 gen1 的 key 沒被展開：**

```
ref-v2.json  FROZEN  params=27  ->  沒指定 gen1 的 19 個 key
ref-v1.json          params=24  ->  19 個
gen0 / 5 個 gen0-* / pq4        ->  20~21 個
```

那 19 個裡有 `optimal_assignment`（+$8,686、58 勝 2 負）、`tiles_per_unit`、
`water_on_demand`、`late_crew_caps`。**讓 gen1 的參數變成唯一預設 = ref-v2
從 Gen0 靜默變成 Gen1**，不會有任何錯誤訊息。

### 做法與驗證

- gen1 的 21 項併進 `gen0.DEFAULT_PARAMS`（`n_structures` 9→12，其餘 20 個是新增）
- `_resolve_params` 搬進 gen0，**保留 `.get` 語意不是 `.pop`** ——
  `test_frozen_full_params_replace_live_gen1_defaults` 直接斷言了回傳值裡
  還有 `_replace_defaults`；`act()` 負責 pop
- 刪 `agents/gen1.py`，19 個 config 的 `entry` 改指 `agents.gen0:act`
- **刪掉 Gen0 線的 9 個對手**（ref-v1、ref-v2、gen0、5 個 gen0-* 消融、pq4）
  —— 留著只會變成量尺靜默位移

三個獨立驗證：

1. `baselines.json` 的三個期末現金（135366 / 124283 / 86199）在合併後的
   `agents.gen0:act` 上**逐項不變**
2. 合併後的 `DEFAULT_PARAMS` 逐項等於 `ref-v11.json` 的 51 個 params
   （ref-v11 本來就是「gen0 + gen1 完整展開」，是現成的獨立基準）
3. 改 entry 前逐檔比對「拿掉 entry 之後的 JSON 是否相同」，19 個全部成立

`pytest` 81 passed（原 82，刪掉 `test_ref_v2_stays_frozen` 那條）。

### 兩條測試改成明寫參數

`test_ladder_wages_keep_land_crew_cap_through_final_day` 和
`test_animal_purchase_respects_committed_housing_capacity` 原本吃
`DEFAULT_PARAMS`，測的是 Gen0 那組值下的算術（前者被 `late_crew_caps` 壓到 8、
後者 `n_structures` 9→12 讓餘位從 0 變 3）。**斷言強度沒有放寬** ——
改成把要測的參數寫死，反而不再受未來改預設影響。

### ⚠️ 留著沒處理的洞

`docs/CLAUDE.md` 寫「凍結量尺 params **完整展開**，不指向 `DEFAULT_PARAMS`」
—— **這句話是假的**，`ref-v3..v11` 各有 19 個 key 落回預設。改那 19 個預設值
會讓所有凍結尺同時位移。這輪照「前期階段凍結量尺意義不大」的決定不處理。

要修：從最新一輪的 rollout 抽一批局當 value 的驗證集，跟 prior 的固定量尺
分開報。

## 15. 把量尺換成「網路自己的盤面」之後，兩個結論被推翻

`docs/CLAUDE.md` 的 Expert Iteration 第 1 階段看的是 top-k 涵蓋率。要進
Phase 2（search）之前先把那個數字量在**對的分布**上 —— search 會遇到的是
網路自己走出來的盤面，不是 gen1 的。

新增 `tools/prior_eval.py`：拿一份 checkpoint 去考另一批資料，不訓練。

### A/B：洩漏 vs 分布，是分布

收兩批全新 seed（200~299，各 100 局）：

    data/dagger/gen1-val    --policy gen1 --expert gen1    gen1 開車
    data/dagger/e2e-val     --policy e2e  --expert gen1    網路開車（round5 權重）

| 考卷 | 誰開車 | seed | op argmax | op top3 | market recall | value RMSE |
|---|---|---|---|---|---|---|
| 舊量尺（round0 的 6 局） | gen1 | 0~199（洩漏） | 0.8780 | 0.9937 | 0.8701 | $19,010 |
| gen1-val | gen1 | 200~299 | 0.8793 | 0.9938 | 0.8820 | $17,443 |
| e2e-val | **網路** | 200~299 | 0.8104 | **0.9834** | **0.3767** | **$12,394** |

🩸 **§14 說「驗證集洩漏讓絕對數字偏樂觀」是錯的。** 換成全新 seed 幾乎沒變
（0.8780 -> 0.8793、0.8701 -> 0.8820）。偏差全部來自「量在 gen1 的盤面上」。

value RMSE 在網路自己的盤面上**反而比較好**（$12,394，dummy $31,303 = 39.6%；
gen1 盤面是 $17,443 / $30,774 = 56.7%）。合理 —— 訓練資料裡 1,200 局有 1,000 局
是網路開車的。

### market recall 0.3767 是量測假象

標籤是「expert 在**這一個回合**看到這個盤面會不會下單」，而 `gen0._market`
每回合重算：種子還是 0 它就再說一次。網路只要慢一步，同一筆需求會在後面
好幾個回合又點亮，分母被灌大。

expert 每盤面想下的單：gen1 自己的盤面 0.440 筆、網路的盤面 **1.263 筆**。

實際送出的訂單（round5 對戰 log，8 局，一局平均）：

    HIRE        288.9 / 287.5      BUY_PRODUCT   15.1 / 13.0
    SELL        106.8 / 102.5      BUY_ANIMAL     9.6 /  7.8
    BUY_SEED     87.1 / 105.6      BUY_LAND       2.1 /  2.0
    合計        509.6 / 518.4      （左 = 網路，右 = gen1）

**訂單量幾乎一樣。** 唯一實質落差是 `BUY_SEED` 少 17.5%。

### 逐 op 門檻校準 —— 負面結果

新增 `tools/market_calibrate.py`：逐 op 掃 F-beta 最佳切點。
`agents/gen2_model.market_thresholds()` 多接一層 `market_threshold_ops`。

依據是逐 op AUC 在網路自己的盤面上有 **0.847~0.999**（排序幾乎完美）但正例的
logit 中位數多半是負的（`BUY_SEED CARROT` -2.08、`SELL WOOL` -3.01、
`BUY_ANIMAL GOOSE` -3.41）。

結果（round5 權重，20 個種子 = 40 局，對 gen1）：

| | market F1 | recall | 每盤面下單 | 期末現金 |
|---|---|---|---|---|
| 門檻 0（`e2e`） | 0.5172 | 0.368 | 0.457 | **80,436** |
| `e2e-cal10`（beta 1） | 0.5696 | 0.654 | 1.397 | 47,478（min 0） |
| `e2e-cal20`（beta 2） | 0.5028 | 0.806 | 2.378 | 48,382（min 0） |

🚫 **調門檻讓期末現金掉 41%，還會破產。** recall 不是遊戲目標，多買要花錢。
兩個 config 留著並在 `note` 裡標明是負面結果，免得有人再試一次。

⚠️ 開發過程踩到的：`tools/market_calibrate.py` 一開始用 `paths[:half]` 對半切，
但檔名是 `{policy}-{對手}-{seed}.npz`，`sorted()` 之後是按對手分群 —— 前半全是
`ladder-top-a`、後半全是 `starter`。症狀是 holdout 的 F1 反而比 fit 高。
改成 `paths[0::2]` / `paths[1::2]`。

### 對 Phase 2 的結論：prior 可以用了

在 search 真正會遇到的分布上：

- unit op **top3 0.9834 / top5 0.9985** -> 候選開 3~5 個就夠

- value **RMSE $12,394**（dummy $31,303）

## 16. Phase 2 的 gate 沒過：value head 排不動候選

開 `search/` 之前先驗核心假設 —— 「產一堆候選 -> 用 value 挑最好的」。
新增 `tools/value_probe.py`（可重跑）。

### 先確認的前提

- **引擎的 forward model 是決定性的。** 同一個快照 + 同一個 policy 跑三次，
  期末現金完全一樣。回溯做法：`deepcopy(env.state)` + 砍掉 `env.steps`
  多出來的部分 + 把 `status` 設回 `ACTIVE`（`env.done` 是唯讀 property）。
- **速度不是問題**（day 15 中局，單執行緒）：

      env.step（真實動作）  3.32 ms      gen2_model.act 整支   3.54 ms
      deepcopy(env.state)   2.14 ms      gen0.act              0.46 ms
      NumpyPolicy 前向      2.81 ms      env.clone()          13.75 ms（太貴）

  一步 rollout（兩邊都跑網路）約 10.4 ms。候選 6 個 x horizon 24 = 1.5 秒/決策。

### 結果：三個 horizon 都比不搜還差

12 個盤面（seed 7/21/33 x day 12/16/20/24，都取 hour 12），每個產 8 個候選
（6 個 unit 各換第 2 名、強迫下買種子單、以及 argmax），
每個候選**把那局真的打完**拿期末現金當答案：

| | 平均期末現金 | vs prior argmax | 贏/平/輸 |
|---|---|---|---|
| prior argmax（不搜） | 79,561 | — | — |
| H=1 用 value 挑 | 78,485 | **-1.35%** | 5/0/7 |
| H=8 用 value 挑 | 78,422 | **-1.43%** | 7/0/5 |
| H=24 用 value 挑 | 77,989 | **-1.98%** | 3/2/7 |
| oracle（事後最好的） | 81,644 | +2.62% | — |

**訊噪比小於 1。** 候選之間的真實差距約 2,000~5,000，value 的 RMSE 是
$12,394（§15）。

⚠️ **而且 oracle 只有 +2.62%** —— 那是「改一個回合的動作」的上限。
我們離 gen1 差 15.6%，而 §15 量到那個差距是「day 12 之後種子持續買少 17.5%」
造成的。**單回合 rerank 修不了系統性的偏差**，就算 value 完美也一樣。

### 踩到的

🩸 第一次快照取在 **hour 0**，那時 `hands` 是空的（`engine-notes.md` §1），
「換第 N 個 unit」全部變成同一個候選 —— 8 個候選裡 7 個一模一樣，
Spearman 完全是噪音。改取 hour 12。

🩸 第一版只跑 1 個盤面就想下結論（n=8 的 Spearman 95% CI 約 ±0.7）。
改成 12 個盤面 + 決策相關的指標（用 value 挑的 vs 直接用 argmax）。

## 17. 多回合承諾也不通；特徵是夠的；瓶頸是欠訓練

### 「一整天的承諾」上限只有 +1.34%

§16 量到單回合 rerank 的上限是 +2.62%。改問「一次決定接下來 24 個回合的
採購傾向」——新增 `tools/commit_probe.py`，7 種傾向（種子 -1.0 / -2.0 /
+1.0、種子+飼料 -1.5、多賣、多買動物、預設），每個套 24 回合之後恢復預設
打到底，15 個決策點（seed 7/21/33 x day 12/15/18/21/24）：

| | 平均期末現金 | vs 不搜 |
|---|---|---|
| 預設（不搜） | 79,561 | — |
| **oracle（每天都選對）** | 80,628 | **+1.34%** |

而且七個候選**單獨拿去用每一個都比預設差**（-0.27% ~ -3.42%，最好的
「賣 -1.5」贏 0/15）。網路現在的門檻已經比任何一組手調值好。

**評估器是打到底的真實結果，不是 value head** —— day 級決策點只有 18 個，
一次 rollout 從 day 12 起約 3.1 秒，付得起。所以這個上限跟 value 的雜訊無關。

### 特徵夠不夠：夠。我先前的假設是錯的

先量到一件真的事：gen0 買種子用的 `n_crop_tiles` 是
`budget["active_crop_count"]`（**打算**種幾格），不是實際種了幾格。
gen1 的 log（12 局，hour 12）：

| day | 打算種 | 實際種 | 差 | spendable/money |
|---|---|---|---|---|
| 6 | 13.0 | 13.0 | 0 | 0.62 |
| 9 | 38.0 | 13.0 | **+25.0** | **0.11** |
| 12 | 52.0 | 18.3 | **+33.7** | 0.48 |
| 15 | 52.0 | 43.2 | +8.8 | 0.67 |
| 27 | 52.0 | 29.3 | +22.7 | 0.95 |

day 9 買地之後「打算種」從 13 跳到 38，而 `contracts.SCALAR_FIELDS` 只有
`n_crop_tiles`（實際）。看起來像是「網路少了關鍵特徵，而且會自我強化」。

🩸 **但線性 probe 推翻了這個假設。** 4 局 gen0 self-play、720 個樣本、
3/4 訓練 1/4 驗證，從現有 75 個 scalar 線性回歸：

    active_crop_count   R² 0.992   RMSE 1.6 格   （真實標準差 17.5）
    spendable           R² 1.000   RMSE $196     （真實標準差 $23,152）
    只用 n_crop_tiles   R² 0.623

**一個線性層就算得出來**，網路是非線性的而且還多看 38 個 spatial channel。
資訊夠，只是沒學好。不需要動 `contracts.py`（那會 ENCODER_VERSION += 1
並且讓 1,200 局的資料全部作廢重收）。

### 湊起來：損失攤在幾百個回合上，不集中

    單回合 rerank 上限        +2.62%
    一整天承諾上限            +1.34%
    七種採購傾向單獨用        全部比預設差
    特徵夠不夠                夠（R² 0.99+）
    在自己盤面上 op argmax    0.8104
    離 gen1                   -15.6%

沒有任何**單一決策**的介入有超過 2.6% 的空間，但總差距 15.6%。
**每 5 個 unit-turn 就有 1 個跟 expert 不一樣**，一點一點累積成 15%。

### 下一步：模型還沒訓練夠

round5 的曲線：

    epoch 7  loss 1.7052  op 0.8765
    epoch 8  loss 1.6353  op 0.8780   <- loss 還在掉 4%，val 還在升，就停了

867k 參數配 840 萬個 unit 樣本，`--epochs 8 --width 96 --blocks 6`。
**欠訓練，不是資料不夠。** 建議先把模型練滿（`--epochs 24 --width 128
--blocks 8`）再談 search —— search 的上限已經量到是 1~3%，
而逐步模仿還有 15%。
