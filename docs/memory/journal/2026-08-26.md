### `ref-v3` / `ref-v4` 為什麼壞

它們是 `agents.gen0:act` + `"frozen": "2026-08-16"` 的 29 個參數。`frozen` 會讓
`eval/runner.py:142` 設 `_replace_defaults = True`，意思是**完全不套現在的預設值**
（`agents/gen0.py:2246`）。今天的 `DEFAULT_PARAMS` 有 51 個 key，缺的 22 個裡
`oversupply_factor` 在 `agents/gen0.py:922` 和 `:1017` 是用 `params[...]` 直接取的。

`agents/gen0.py:128` 早就寫了註解「ref-v2 / ref-v4 沒有這個 key。要嘛切一版
ref-v5，要嘛移出預設只給 sweep 用」—— 沒人回頭修。**這兩支現在整個 repo 都跑不動。**

### 🩸 `e2e-*` 那 11 支**沒有壞**，是我的審查腳本漏了環境變數

第一版的審查結論寫「11 支 `e2e-*` 全部 `FileNotFoundError: agents/weights.npz`」。
**那是錯的**（22:20 修正）。`agents/gen2_model.py:111` 的 `WEIGHTS_PATH` 是
**模組層級常數、import 當下就決定**：

```python
WEIGHTS_PATH = os.environ.get("KAGGRI_WEIGHTS", ...)
```

沒設 `KAGGRI_WEIGHTS` 就退回 `agents/weights.npz`（不存在）。設了就全部能跑，
實測 `e2e` / `e2e-cal10` / `e2e-restock20` / `e2e-t10` / `gen2_model` 五支都 ✓。

🩸 **推論**：任何自己驅動迴圈、又要用網路當對手的工具，都要在
**import `agents.gen2_model` 之前**設好 `KAGGRI_WEIGHTS`。
`tools/search_game.py` 是對的（頂層沒 import `gen2_model`，
`main()` 第 395 行設完環境變數之後才建 `mp.Pool`，worker 才 import）——
22:20 用 `mp.Pool` 實測 worker 裡的 `WEIGHTS_PATH`
和 `value_head.2.bias`（0.5560864806175232）確認過。

### builtin 對手要另外處理

`starter` / `pass` / `random` 的 `build_agent` 回傳的是**字串**，給 `env.run([...])`
用的。自己驅動迴圈的話要去 `env.agents[name]` 拿 function，**而且它們只吃 `obs`
一個參數**，簽名跟 `agents.*:act` 不一樣。已在 `tools/search_game.py` 用
`inspect.signature` 判分支。

## 4. 最後採用的 12 支對手，以及為什麼

理論上對手集合控制三件事，**第三件是 search 特有的**：

1. **狀態分佈**（DAgger 的標準論證）—— 要接近部署時的對手分佈
2. **value target 的散佈** —— 強度全一樣的話回歸學不到鑑別度
3. **標籤本身是對手的函數** ← search 特有

第 3 條：`search_action` 的評分是「套上候選動作，用 rollout policy 打到季末」，
而打的過程裡**對手也在動**。所以搜出來的是**對這個對手的 best response**。
網路只看得到盤面、看不到「我在跟誰打」，所以它學到的是那些 best response 的
平均 —— 那個平均逼近的是「對混合分佈的 best response」。

`config/ladder-top.json` 裡有 **8 支真實 ladder 頂端 replay**（rating 2979~3229、
7 個不同 episode、8 個不同玩家，其中一支養鵝、一支種瓜）。🩸 **它們是 inline
spec，`eval/runner.load_spec` 只找 `config/opponents/<name>.json`（`:77`），
所以叫不動。** 今天抽出來成獨立檔。

`config/sweep-hire.json` 的 `hire-N`（只改 `max_hands`，預設 12）是一條 13 倍
跨度的強度梯（2026-08-21 實測，`temp/20260821-150053_e2e_vs_sweep-hire/summary.txt`）：

```
hire-0    6,929      hire-8    85,088

hire-4   61,740      hire-16   70,290
starter   ~3,400
```

`hire-0` 嚴格優於 `starter`：現金差不多低，但它是**真正的 gen0 行為**（會移動、
種、賣、下市場單），`starter` 只在腳下反覆種胡蘿蔔、不移動。

## 6. 推翻了昨天的兩個推論

### 6.1 replay 對手**沒有**被 search 打殘

昨天推的鏈子是：search 改得越多 → 局面偏離原軌跡越大 → replay 的 `BUY_*`/`HIRE`
訂單失敗越多 → 它越弱 → 我們的增益是假的。

實測相反：

```
                    我方增益     對手變化
會反應（hire-*） n=8   +24,926     +3,687   （p=0.0078，判得出來）
replay        n=12   +26,501    +14,107   （p=0.092，判不出來）
```

**兩種對手都變得更有錢。** 增益不是靠壓低對手來的。

🩸 但要注意 replay 那組變異極大（−32,556 ~ +64,462），n=12 判不出來。這條沒有
被證實也沒有被推翻，只是「打殘」那個方向被推翻了。

### 6.2 replay 的中途現金不是強度指標

`ladder-top-a` 在 day 4 手上只有 $33，期末卻是 118,498。它開局就把錢全花掉
（`agents/replay.py` docstring：`steps[1]` 的 money 已經是 22）。**只能看期末。**

### 6.3 `board_reward` 不看對手

```python
"board_reward": np.full(n, mine / 100_000.0)     # harness/rollout.py:185
"board_win":    np.full(n, 1 if mine > theirs else ...)
```

`board_reward` 是**我方期末現金 ÷ 100,000**，對手只透過「影響我方賺多少」間接影響它。
`board_win`（1/−1/0）才是相對的。

這批的散佈比舊資料**窄**：

| | 範圍 | 低於 0.5 |
|---|---|---|
| 舊 DAgger（抽 200 局） | 0.144 ~ 1.334 | 17.5% |
| 這批 | 0.788 ~ 1.553 | **0%** |

要有低的 `board_reward` 得有「我們打得很差」的局，而 search 的作用剛好是防止那個。
對 value head 不利。**但不擋這次訓練** —— `gen2_model.act` 出手只用
op/qty/market（`agents/gen2_model.py:395-400`），而 value head 在 08-24 就測出來
排不動候選。

`board_win` 是 **10 勝 10 負**，對手強度配得算準。

### 什麼時候換 self-play

不是時間，是**我們追上對手池的強度**。現在 `gen0 + search` 對 `ladder-top-a`
是 76.9%，還差 23%。這個階段固定的強 replay 是資產 —— 它把真正的強手打法注入

## 12. 斷點續跑（23:30 做好）

### 為什麼

`--policy net` 一局要 2.1 小時（`--hours 12`）或 8.3 小時（`--hours 6,12,18,22`），
而 npz 是**整局跑完才寫**。10 個 worker 同時各跑一局 -> 任一時刻最多有
10 局的計算沒存。過夜跑到一半斷電就整晚白費。

### 做法：記動作、重播，不序列化 env

引擎、`agents/gen0.py`、`agents/replay.py`、`serving/npz_forward.py` 全部是
決定性的。所以**不需要序列化 `env`** —— 只要記下我方每個 search 回合送出的
動作，重建 env 之後依序重播就回到同一個狀態。沒搜的回合由 policy 決定，
也是決定性的，可以重算。一局 30~120 個動作，寫進**現有的** progress JSONL。

🩸 **跨行程的決定性是實測過的，不是假設。** 2026-08-26 跑了三批
（22:10 / 22:59 / 23:22，三組不同的行程），對照組十局的期末現金逐位元組相同：

```
seed 0  hire-0     120,743   120,743   120,743
seed 4  kawashigi   50,272    50,272    50,272
seed 9  peikopon    73,196    73,196    73,196
```

使用者問「為什麼基準跟上一次一模一樣」才注意到這件事 —— 那正好是這個做法的
前提條件。（也因此三批之間可以直接比搜尋版的成績，對照組是同一把尺。）

### 改了什麼（`tools/search_game.py`）

| | |
|---|---|
| progress 多記 `action` | 續跑靠這一欄重播 |
| `--resume RUN_DIR` | 已完成的局跳過、跑到一半的局重播接續、沒開始的從頭跑 |
| `run_dir/config.json` | 開跑時寫。續跑**強制用它**，不吃這次的旗標 |
| `progress/STOP` | 跑到下一個決策點就乾淨收工，之後續得回來 |
| RNG 逐決策點播種 | `default_rng(rng_seed + seed * 10007 + n_searched)` |
| `_read_resume()` | 把 progress 讀成續跑狀態 |

🩸 **`--hours` / `--policy` 之類的設定續跑時不能變。** 變了的話重播的動作會落在
不同的回合上，整局狀態就對不起來 —— **而且不會報錯，只會安靜地產出垃圾**。
所以續跑一律讀 `config.json`。

🩸 **RNG 為什麼要改。** 原本是整局共用一個 `default_rng(rng_seed + seed)` 一路
往下抽。續跑時前面的決策點不呼叫 `CAND.generate`，rng 狀態就對不上，多 unit
候選會抽到不同組 —— 不影響正確性（任何候選集合都合法），但續跑就不可重現了。

🩸 **`STOP` 之後不寫 `done`、不寫 npz。** 寫下去會被當成完成的局，之後
`--resume` 就跳過它了。

## 13. 為什麼蒸餾學不會：網路無記憶，而 search 產不出意圖（討論，未實作）

使用者問：「只學有 search 的盤面，但盤面不是有先後順序嗎？它可以學會？」

### 先確認兩件事實

1. **網路是無記憶的。** `agents/gen2_model.py:366` 的 `act(obs, config, params)`
   只吃當下這一格的盤面，做一次前向就決定，沒有任何跨回合狀態。
2. **連「往哪走」都是每回合重新決定的。** round6 用 `--labels immediate` 訓練，
   `op` 是「這一步做什麼」，方向是 44 個 op 裡的選項（dummy 就是 `('WEST', None)`）。

所以**順序在模型裡不存在** —— 訓練時每個盤面是獨立的一筆 (輸入, 答案)，
上場時每回合從當下盤面重新算。「只錄搜過的回合」沒有斷掉任何序列。

### 但因此有一個結構上的限制

網路無記憶 -> **蒸餾要成立，search 找到的那個更好的動作必須是「當下盤面」的
函數。** 如果不是，資料再多也學不會。**這是結構問題，不是量的問題。**

兩個具體的失敗途徑：

**(a) 意圖看不見。** search 說「現在買一顆西瓜種子」，理由可能是「再過 8 小時
有工人空出來可以去種」。那件事不在當下盤面上。而且 search **產不出意圖標籤**
—— `unit_target`（`harness/rollout.py:145-165`：這個 unit 這一段要走去哪一格）
在 search 盤面上一律寫 −1。**我們教了動作，卻拿掉了理由。**

**(b) 只標 4/24 個小時 = 只標片段。** 如果 search 的改良是一串協同動作
（hour 6 買 -> hour 10 走過去 -> hour 14 種），我們只在 6/12/18/22 標答案，
其餘 20 個小時網路照舊做 round6 的老行為，那串接不起來。

### 一個反面證據：網路推得出意圖

round6 的 `target` head（「這個 unit 要走去哪一格」）驗證準確率 **0.8306**
（dummy 0.4355）。所以網路**確實有能力從盤面推斷相當程度的意圖** ——
那個能力是從 gen0 的意圖標籤學來的，而 search 資料剛好沒有那一半。

### 使用者的提議（比我原本的做法好）

我原本提的是「補上 gen0 規劃器的意圖」，但被迫加一條限制：**search 改過的
unit 不能用** —— gen0 說「他要去 47 號格」會跟 search 讓他往反方向走矛盾。

使用者指出：**search 時本來就會讓 round6 打到底，那不就知道工人的去向了嗎？**

對，而且**連 rollout 都不用留** —— search 選完之後真實那一局就繼續往下打，
往下打的就是 round6。所以直接**往後看那一局**：

```
決策點在 hour 6，工人 3 被 search 改成往東走
往後看：hour 7 往東、hour 8 往東、hour 9 停下來 PLANT
  -> unit_target  = hour 9 停下來的那一格
  -> unit_term_op = PLANT
```

正好重建出 gen0 那個 `(dest, final)` 的結構，而且**跟動作標籤天生一致**，
所以**所有 unit 都能標**，不用挑。

🩸 **可以事後補，不用重跑對局。** 這是斷點續跑（§12）的意外好處：progress 現在
記下了每個 search 回合送出的動作，所以已完成的局可以重放一次（幾秒鐘），
把工人的去向讀出來補進 npz。

### 三個要處理的細節

1. **unit 身分要跨回合對得上。** `contracts.encode_units` 是「農夫第一、
   然後是雇工」。雇了新工人之後索引會不會位移**沒查過** —— 位移的話
   「往後看工人 3」會看錯人，**而且不會報錯**。這是第一件要驗的事。
2. **有些 unit 走到日終都沒停下來** -> 沒有終點動作，標 −1。gen0 的資料本來
   就有 4.2% 是這樣。
3. **讀出來的是「round6 的意圖」不是「最好的意圖」。** 往後打的是 round6
   （加上後面幾個決策點的 search），所以標籤裡混著 round6 自己的缺點。
   gen0 的版本有同樣的毛病（那是 gen0 的意圖），差別是這個至少跟動作一致。

### 一個還沒驗證的假設

`target` head **上場時根本不用**（`agents/gen2_model.py:395-400` 只用
op / qty / market）。補它的價值是當**輔助任務**，讓 trunk 學會把意圖編進表示裡，
間接幫到 op。**那是假設，沒驗過。**

驗法：訓兩版（有補 / 沒補），比 op 在 search 盤面上的命中率
（`tools/search_label_probe.py`）。

### 這件事在選項裡的位置

§8 列的四個選項之外，這是第五個，而且它針對的是**別的東西** ——
§8 的 A/C（加權）處理「訊號被淹掉」，這一條處理「訊號本身缺一半」。
兩者不互斥。

優先順序（使用者說先討論、先不做）：

1. **先量「到底學不學得會」** —— 早上那批跑完直接重跑 data-scaling 曲線。
   曲線往上爬才值得投資後面幾項；又是平的話，問題可能在編碼器。
2. 補意圖標籤（這一節）—— 便宜，而且可以事後補。
3. 加權 + 混舊資料一起訓（§8 的 A/C）—— 今天只試了純微調，混舊資料沒試過。
4. 搜更多小時 —— 成本線性，最貴。
