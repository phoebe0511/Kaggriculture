## 1. 系統全景

這個專案其實是**兩個獨立的系統**，只透過一個檔案溝通：

```
╔═══════════════════════════════════════════════════════╗
║  系統 A：訓練工廠（跑在我們家，用 GPU，跑幾天）         ║
║                                                       ║
║   ┌──────────┐    ┌──────────┐    ┌──────────┐        ║
║   │ 對戰產線 │───▶│ 棋譜倉庫 │───▶│ 訓練器   │        ║
║   │self-play │    │ replay   │    │ PyTorch  │        ║
║   └────▲─────┘    └──────────┘    └────┬─────┘        ║
║        │                                │              ║
║        └────────── 新模型回填 ──────────┘              ║
╚═══════════════════════════════════════════╪═══════════╝
                                            │
                                    weights.npz（一包數字）
                                            │
╔═══════════════════════════════════════════▼═══════════╗
║  系統 B：比賽用程式（跑在 Kaggle，CPU only，每回合幾秒）║
║                                                       ║
║   obs ──▶ 編碼 ──▶ numpy 前向 ──▶ 搜尋 ──▶ action     ║
╚═══════════════════════════════════════════════════════╝
```

**關鍵認知：系統 B 才是我們要交的東西，而且它非常小。**

系統 B 大概 500~800 行，不能 import torch，必須在時限內回應。
系統 A 可以隨便肥，跑多久都沒關係。

**兩邊唯一的共用程式碼是「編碼」那一塊**——因為訓練時和比賽時必須用完全一樣的方式把 obs 轉成數字。這也是最容易出事的地方（見 §4）。

## 2. 模組清單

```
encoding/        obs ↔ 數字陣列的轉換     ⚠️ 兩邊共用
harness/         平行 self-play，產棋譜
serving/         inference server、submission 打包
agents/          第 0 代規則式 AI、搜尋演算法、經濟評估器
model/           網路定義、訓練
eval/            對戰天梯、統計判定
contracts.py     介面定義（凍結）
```

### 遊戲規則從哪裡來

**直接 import 引擎，不抄。**

```python
from kaggle_environments.envs.kaggriculture.kaggriculture import (
    CROPS, ANIMALS, MARKET_PARAMS, market_price,
)
```

抄一份常數表會有兩個風險：抄錯、上游改版沒跟上。兩者都**不會報錯**，只會表現成
「分數莫名其妙上不去」。上游 1.30.1 → 1.32.6 就改過 COW 成本（600→400）
和四項產品的價格曲線。

引擎裡沒有、要自己寫的只有兩樣，都放在 `agents/`：

```python
def profit_per_hour(product, market, inventory) -> float:
    """種/養這個東西，換算成每投入一小時能賺多少"""
```

每回合重算，是第 0 代 AI 的決策依據，也是搜尋的評分基礎。

另一樣是搜尋用的 forward model —— 引擎的 `interpreter()` 就地修改 state、
一次處理兩個玩家、每步固定跑完市場撮合和城鎮消耗，不能拿來做 what-if 展開。

### encoding/ — 最危險的模組

把遊戲現況轉成網路吃得下的數字。分兩路：

**空間路**：農場是格子，每格疊上多層資訊

```
channel 0: 這格是不是我的地
channel 1: 這格有沒有作物
channel 2~6: 作物種類（小麥/玉米/... 各一層，有就是 1）
channel 7: 生長進度 (0.0 ~ 1.0)
channel 8: 澆過水了嗎
channel 9: 施過肥了嗎
channel 10: 有沒有雞舍
channel 11: 有沒有牧場
channel 12: 我的農夫在這嗎
channel 13: 幫手在這嗎
channel 14: 離最近水源幾格（先算好，網路不用自己推）
...
```

輸出形狀 `[C, H, W]`。這就是給 CNN 吃的東西——跟影像是 `[RGB, 高, 寬]` 完全同一個道理，只是我們的「顏色」有十幾種。

**純量路**：不是格狀的資訊

```
現金、各產品庫存、目前市價、過去 24 小時價格變化、
今天第幾天、現在幾點、剩幾回合、有幾個幫手
```

輸出形狀 `[D]`，給 MLP 吃。

### agents/ — 兩種 AI

**第 0 代（規則式）**：純 if-else + 貪婪排程。用來暖身，產第一批棋譜。

**正式版**：網路 + beam search。

### harness/ — 對戰產線

多行程平行跑 self-play。**這是整個專案的效能瓶頸**，詳見 §3。

### serving/ — 上場前的加工

- inference server：訓練時用，讓多個 worker 共用一張 GPU
- submission 打包：把 PyTorch 模型轉成 `.npz` + numpy 前向程式碼

### model/ — 網路

```
        ┌─ CNN ────┐
spatial ┤ 4~6 層   ├──┐
        └──────────┘  │
                      ├─→ 合併 ─┬─→ policy_type   [18]     「做哪種動作」
        ┌─ MLP ────┐  │         ├─→ policy_target [H,W]    「對哪一格」
scalar  ┤ 2 層     ├──┘         ├─→ value         [1]      「這局面值多少」
        └──────────┘            └─→ aux           [k]      「輔助練習題」
```

**動作為什麼拆成兩個 head**：`18 種動作 × H×W 個格子` 直接展開會有幾千種組合，網路很難學。拆成「先決定做什麼」+「再決定對哪格」，參數量少兩個數量級。

**aux head 是什麼**：讓網路順便預測「12 小時後小麥價格」和「這塊田最後會收成多少」。這兩個答案我們**用公式算得到**，等於免費送網路的練習題。有這些額外訊號，網路學得快很多。

網路大小控制在 100 萬~300 萬個參數。

## 3. 效能瓶頸在 CPU，不在 GPU

**這點反直覺，但很重要。**

一代訓練要 5,000 局，每局 720 回合 = **360 萬次遊戲模擬**。而遊戲引擎是純 Python 寫的，慢。

相比之下，訓練一個 300 萬參數的小網路，GPU 幾分鐘就跑完。

> **所以那顆 20 核 CPU 比顯卡重要。**

### 對戰產線的架構

```
┌───────────────────────────────────────┐
│  24 個 worker 行程                     │
│  只跑遊戲引擎，純 CPU                  │
│  ⚠️ 完全不 import torch                │
└──────────────┬────────────────────────┘
               │ queue：送出一批 obs
               ▼
┌───────────────────────────────────────┐
│  1 個 inference server 行程            │
│  獨佔 GPU，一次算 256 筆               │
└──────────────┬────────────────────────┘
               │ queue：回傳 policy + value
               ▼
          棋譜寫入磁碟
```

**為什麼不讓每個 worker 自己載模型？**

- 24 份 PyTorch 各佔幾 GB 記憶體
- GPU 每次只算 1 筆，利用率極低
- 吞吐差距**數十倍**

### 必須達成的數字（Week 2 結束前）

| 情境 | 目標 |
|---|---|
| 第 0 代規則式 self-play | **> 5,000 局/小時** |
| 網路 + 搜尋的 self-play | **> 1,500 局/小時** |

**達不到的話整個訓練循環會餓死。這是這類專案最常見的死法。**

## 4. 介面凍結（`contracts.py`）

三個函式，**定下來就不准單方面改**：

```python
ENCODER_VERSION = 1

def encode(obs) -> tuple[np.ndarray, np.ndarray]:
    """現況 → (空間陣列 [C,H,W], 純量陣列 [D])"""

def legal_mask(obs) -> tuple[np.ndarray, np.ndarray]:
    """現況 → (哪些動作能做 [18] bool, 哪些格子能操作 [H,W] bool)"""

def decode(type_idx, target_idx, obs) -> dict:
    """(動作編號, 格子編號) → 引擎吃的動作格式"""
```

### legal_mask 為什麼是獨立的一等公民

**遊戲引擎遇到做不到的動作時，是靜默忽略——不報錯、不警告，什麼都不說。**

```
我們的程式：這回合蓋雞舍
引擎：（錢不夠，忽略）
我們的程式：好，蓋完了，繼續
```

**我們以為蓋了。實際上什麼都沒發生，而且完全不知道。**
這種 bug 不會崩、不會報錯，只是最後分數莫名其妙很爛，查三天查不出來。

所以規則是：**送出前自己檢查，不合法就主動崩潰。**

```python
assert legal_mask(obs)[0][action_type], f"turn {t}: {action_type} 非法"
```

**與其讓引擎默默吞掉，不如讓自己的程式大聲叫。**

第二個用途是給網路用：網路輸出 18 個分數，但其中有些動作根本不能做（例如已經在地圖邊界還要往北走）。先用 mask 把不能做的劃掉再選最高分，**網路就不可能吐出非法動作**，不用浪費訓練量去學邊界在哪。

### channel 版本規則（最重要的一條）

訓好的模型**綁死在 channel 順序上**。改順序 = 所有模型作廢。

```
✅ channel 只能往後加
❌ 不准調換順序
❌ 不准刪除
```

- 每次加 channel → `ENCODER_VERSION += 1`
- 存模型時把 version 寫進檔案
- **載入時版本不符 → 直接拋錯，不要試圖相容**

> 這條規則會省下至少一次「為什麼模型突然變爛」的通宵。

## 5. 比賽端的硬限制

| 限制 | 對策 |
|---|---|
| 只有 CPU，單一檔案 | 模型存 `.npz`，用 numpy 做前向 |
| **不准 import torch** | 載入要好幾秒，會吃掉第一回合的時間額度 |
| 每回合有時限 | 搜尋必須是 anytime：先產保底解，有時間才多想 |
| 引擎靜默拒絕非法動作 | 送出前必過 `legal_mask` |
| log 長度有上限 | submission 的 `LOG_LEVEL` 固定為 0 |

### anytime 搜尋長怎樣

```python
def act(obs):
    t0 = now()
    
    # 第 1 步：網路跑一次，馬上有個能用的答案（保底）
    policy, value = forward(encode(obs))
    best = argmax(policy * legal_mask(obs))
    
    # 第 2 步：有剩餘時間才展開搜尋
    while now() - t0 < BUDGET:
        candidate = expand_one_more_node()
        if candidate.score > best.score:
            best = candidate
    
    return best
```

**因為第 1 步就有答案，所以絕對不會超時。** 這是選 ExIt 方法的一個結構性好處：網路本身就是 fallback。

### 增量修補

相鄰回合的局面差異極小（就過了一小時）。**修補上一回合的搜尋結果，不要每回合從零重算。**

這比任何 timeout 保護機制都更能解決算力問題。
