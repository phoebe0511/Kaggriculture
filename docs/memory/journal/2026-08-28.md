## 2. 第二輪：seeds 54、holdout 加滿 8 支

```
temp/cma/20260827-164222
--seeds 54 --popsize 14 --workers 10 --sigma0 0.08
--warm-start temp/cma/20260827-130938/gen_0030.pkl
一代 756 局 / 539 秒   跑到第 108 代放 STOP
```

`best_so_far`：−28,324（第 1 代）→ −12,875（6）→ −8,654（68），之後 **39 代沒動**
（sigma 0.0128）。

🩸 **第一輪和第二輪的分數不可比** —— 24 個 seed 和 54 個 seed 量的是不同的東西。
第二輪第 1 代的 −28,324 大致就是「第一輪第 30 代那組參數改用 54 個 seed 重量」。

- ❌ **不是**「專門吃 ladder-top-a」—— 沒訓練過的 7 支也跟著升
- ❌ **不是**「吃 replay 不會反應」—— `gen1` 會反應，也升

**訓練只打一支對手（`ladder-top-a`）這件事，事後看是可以接受的。** 但那是
holdout 給的事後判斷，不是設計上的保證。

第 60 → 100 代是白跑的：train 只 +1,151，holdout 和 5 支往回走。

### 這一輪改的三件事

| | 為什麼 |
|---|---|
| `--seeds` 24 → 54 | 第一輪的過擬合根因，實測需求 |
| `HOLDOUT_TEAMS` 3 支 → 8 支 + `gen1` | 原本只有 tetsuya/recursion/utkarsh，**看不到對 rating 最高的 kawashigi / thomas 有沒有效**。成本每次 checkpoint 多 100 局 ≈ 55 秒（+2.4%） |
| 新增 `--warm-start` | 借上一輪某一代的最佳解當起點，**covariance 重來、sigma 重設**。舊 covariance 是在雜訊排序下學的，而且正是過擬合的方向 |

## 5. 驗收：改進是真的，但對 replay 的數字灌水八成

seed 2000~2039 ×2（正反手配對），跟 CMA 的 train（0~53）和 holdout
（1000~1039）完全不重疊。

### 對 8 支 ladder replay（**不會反應**）

              我方       對手     現金比    勝率     雙方合計
gen1        64,432    111,344     57.9%     3.0%    175,777

🩸 **現金比的改善有 81% 來自壓低對手，而且雙方合計少了 16,295。**

### 對 `gen1`（**會反應**，= `agents.gen0:act` 走 `DEFAULT_PARAMS`）

```

### 判讀

| | 壓低對手佔比 | 雙方合計 |
|---|---|---|
| 會反應的對手 | 32% | **+6,825**（變大） |
| 開迴路 replay | 81% | −16,295（變小） |

**兩件事同時成立：**

1. **改進是真的。** 對會反應的對手 +12,716、勝率 95.0%，而且餅變大 ——
   那是多產出來的，不是搶來的。
2. **對 replay 的 57.9% → 76.7% 被灌水了。** 八成來自 replay 買不到東西、
   雇不到人。真人會改買別的，那一段不會轉移。

真實的期望改善介於 **+4,815**（對 replay 我方自己的增量）和 **+12,716**
（對會反應的對手）之間；`3.0% → 14.4%` 的勝率提升應該是高估。

**`cma1-g50` 兩個測試都贏 `cma1-g68`**（+12,716 vs +8,030），加上 CMA 期間
holdout 也比較好 —— 出貨用 g50。

⚠️ `gen1` 自打的勝率是 **46.2% 不是 50%**。同一支 agent 兩邊對打、正反手都跑，
理論上該剛好一半，差 3 局（37/80）。可能是引擎 per-unit lockstep 的先後順序
（`kaggriculture.py:545`）造成的位置偏差，或有平手。**沒查** —— 但它讓上面
所有勝率有約 4pp 的系統性偏移。

## 5b. 打包：`submission/cma1-g50/`

🩸 **`serving/build_submission.py:157` 會 `rmtree` 整個 `dest`**，而
`submission/` 底下有 `e2e-round6/`（打包好的網路版，含 6 MB 權重）。所以
**開子資料夾**，用 `copy_files(dest=REPO_ROOT/"submission"/"cma1-g50")`
從 Python 呼叫（CLI 沒有 `--dest`）。`submission/main.py`、`gen0.py`、
`e2e-round6/` 都沒有被動到。

參數是**內嵌**在打包出來的 `main.py`（`PARAMS = {...}`），不是放一份 JSON
進去。那不是偏好，是硬限制：Kaggle 用
`exec(compile(raw, path, "exec"), {})` 載入，**exec 環境裡沒有 `__file__`**
（`build_submission` 的 docstring），`main.py` 無從知道自己在哪個目錄，
旁邊放 JSON 也開不起來。

🩸 **`PARAMS` 裡一定要有 `_replace_defaults: True`。** 驗收走的是
`eval.runner.build_agent`，它看到 spec 的 `frozen` 會自動補這一項
（`eval/runner.py:135-137`）；submission 不經過那條路。不補的話這 51 項會跟
`gen0.DEFAULT_PARAMS` 合併 —— 今天是 no-op，但之後 gen0 多一個預設 key，
上場的就跟量過的不是同一個 agent。

### 驗收打包有沒有出錯

`config/opponents/cma1-g50-sub.json` 走 **`builtin`** 分支 —— `build_agent`
直接把路徑交給 `env.run`，用 Kaggle 自己的 `exec` + `sys.path.append(exec_dir)`
載入，跟正式上場同一條路。

🩸 `--a submission/cma1-g50/main.py` 那種寫法**會炸** —— `load_spec` 走
`__import__`，找不到同目錄的 `gen0`。一定要用 `builtin` 的 spec。

因為引擎是決定性的，判準可以下得很硬：**打包版對 ladder 的 640 局必須跟

### 關於 self-play（討論，未實作）

🩸 **08-27 的負面結果不能拿來說 self-play 不行。** 那是兩件不同的事：

```
search 失敗的地方   「在一個盤面上 51 個動作哪個最好」
                    要在 ±4,572 的擺盪裡分辨幾百元 -> 需要 656 次延續
RL 需要的           「幾百萬步平均下來梯度方向對不對」
                    雜訊會被樣本數平均掉
```

真正卡住的是**模擬速度**：

```
引擎純 Python，一局 720 步
規則式   ~1.5 局/秒（10 workers）= 1,080 步/秒
帶網路   gen2_model.act 約 11 ms/步 -> 約 0.3 局/秒 = 216 步/秒
10^8 步 / 216 = 129 小時 ≈ 5.4 天（一次嘗試，不保證成功）
```

`serving/` 的 inference server 架構就是為此準備的（`docs/CLAUDE.md`：self-play
worker 不 import torch、走 queue batch）。但 `docs/CLAUDE.md` 明確寫
「不要建議 PPO from scratch」，而且一次下注 5 天。**先做 §6 的量測再決定。**

### 為什麼全域 PLANT 配對沒用

`PLANT` 是最後一層（`_PRI` = 9），輪到它時 `free` 平均只剩 **1.48** 個 unit，

算出來幾乎是同一個答案 —— **沒有最佳化空間**。問題在上游：unit 在更高優先序的
層就被吃光了。

### 為什麼密集配置反而更糟

`agents/gen0.py:1500-1503`：

> unit 0（farmer）固定從 NW 開始，其餘依 index 輪流分區。**hands 每天也是
> NW/NE/SW/SE 內角輪流出生**

**工人本來就是跨象限輪流生出來的**，所以 `active_crop_tiles:384` 的 round-robin
不是在浪費效率，它是在配合工人的分布。把工作集中到一個象限 = 另外兩個象限出生的
工人每天走半張圖上班。兩個 round-robin 是耦合的，不能只動一邊；而「工作集中 +
工人也集中」就是 `quadrant_zoning`，測過，更差。

**沒有一個能把作物格從 33 推到 63，也沒有一個能把現金推過 91,110。**

### 這代表什麼

差別不在執行效率，在**經濟判斷**。同樣 75 格：

- 對手撒 143 顆便宜 WHEAT 種子（$1,430），收 447 個賣掉（$20,753），
  **超產 447 個，均價只從 $49.9 掉到 $46.4** —— 幾乎沒掉
- 我們的 `_plan_basket` 只配 33 格，WHEAT 10 格封頂

`_plan_basket` 的 docstring 自己就寫著「WHEAT / EGG 這種 `above_func = log`
的，超產也幾乎不掉價 → 一直有價值」。**模型知道這件事，但配置沒有反映它。**
下一個要查的就是這個矛盾 —— 那是一個函式，不是一個架構。

### 對 self-play 的判斷

**現在不是時機。** 距離 2026-09-30 截止還有 33 天，一次 RL 嘗試 5.4 天

## 33. PPO：軌跡收得起來、訓練迴圈接通了，路上撿到一個會讓整條路失效的洞

§32 的四個待辦全部做完。順序是「收軌跡 -> 發現 market head 根本沒進分佈 ->
補上 -> 接訓練迴圈 -> 發現自對局沒訊號 -> 補固定對手」。

### 33.1 🩸 market head 原本完全拿不到 gradient

`contracts.decode_market_orders`（`contracts.py:412`）是**門檻 + argmax**，
完全決定性。原本的 rollout 直接把網路的 market logit 丟進去，所以：

```
取樣的（有 logprob）  每個 unit 的 target(100) × op(44)
決定性的（沒 logprob） HIRE / BUY_LAND / BUY_SEED / SELL / BUY_ANIMAL …
```

policy gradient 只走得到有 logprob 的那一半。**這正好是使用者要 PPO 改善的
三件事（土地使用率、種什麼、hire 幾人）全部落在沒 gradient 的那一半。**

實測（隨機初始、2 個 env、72 步）：

| | 每步 unit 數 |
|---|---|
| market 決定性 | **1.00** —— 從頭到尾只有 farmer，一個人都沒雇 |
| market 進取樣 | **5.45** |

修法：market 拆成階層式分佈，

```
log p(market) = Σ_{j 合法} log Bern(present_j)
              + Σ_{j 合法且 present_j=1} log Cat(qty_j)
```

`model.ppo.sample_market` 取樣、`model.ppo.market_logp_entropy` 算 logprob 和
entropy。**取樣結果改寫成 logit 再交給 `decode_market_orders`**
（present 用 ±1、qty 用 one-hot），這樣數量 clamp、HIRE 要送 n 筆那些規則不用
重寫一份 —— `contracts.py` 是凍結的，也不能改。

### 33.2 🩸 隨機初始的自對局沒有 reward 訊號

自對局兩邊同一份權重，random policy 開局就把 $3,000 全部花在雇工和買東西上，
之後兩邊現金都是 0，整局 0 對 0。實測（4 條軌跡、120 步）：

| | 非零 reward 的步 | adv std | ret 範圍 |
|---|---|---|---|
| 自對局（隨機初始） | **1.9%** | 0.084 | [−1.00, +1.00]（只剩期末 bonus 的 sign） |
| 打 `cma1-g50-wt` | **26.9%** | 0.215 | [−1.15, −0.06] |

所以 `VecRollout` 加了 `opponent` 參數，`ppo_train` 的 `--opponent` **預設就是
`config/params/cma1-g50-wt.json`**，不是自對局。單雙數 env 輪流坐先手／後手。
對手用 `eval/runner.py` 的 `load_spec` / `build_agent` 載，凍結 spec 會自動帶
`_replace_defaults`，跟 ladder 用的是同一條路。

### 33.3 收了什麼、多大

`model.ppo.Trajectory`：步層 `[T]`、unit 層攤平成 `[U]` 加一條遞增的
`unit_step` 指回第幾步（跟 `net.forward` 的 `unit_board` 同一個形狀）。

```
spatial [T,38,10,10] float32   15.2 KB/步  <- 佔 98%
scalar  [T,75]                  0.3 KB/步
unit 層 pos/feats/兩個 mask/兩個 idx        每 unit 約 160 B
market  legal/present/qty [T,21]           每步 210 B
```

一局 720 步 × 2 個 player ≈ **22 MB**，16 個 env 一輪 **350 MB**。

`RolloutBatch` 把多條軌跡攤平，minibatch **抽的是步不是 unit**（PPO 的 ratio
是整步聯合動作的，同一步的 unit 拆到不同 minibatch 會算出錯的 logprob），
用 CSR（`unit_start` / `unit_count`）做不定長的 gather。

### 33.4 驗收：rollout 存的 logprob 和 update 重算的要相同

這是整條路的地基 —— 對不上**不會報錯**，只會表現成「跑得動但學不起來」

market 有進分佈（每步 unit 數 > 1.5）
reward 零和、GAE 形狀
CSR 的 ragged gather 配對正確（用假資料，印記是 op_idx）
```

沿用 `worker-count` 那則記憶的 10。

換算 10^8 步（139,000 局）：單行程 85 小時，10 行程 **14.7 小時**。

🩸 兩個踩過的坑寫在模組 docstring 裡：`mp.Pool` 不能在 `silenced()` 裡建
（Windows spawn 會繼承 dup2 過的 fd，2026-08-27 卡了 30 分鐘）；每個 worker
要 `torch.set_num_threads(1)`。

### 34.2 spatial 存 float16

軌跡的 98% 是 spatial（15.2 KB/步）。存 float16 少一半：**一局 11.1 -> 6.1 MB**，
多行程送回主行程的量同步減半。

🩸 **前向也要吃 float16 還原後的值**（`VecRollout.half_obs`），不然 update
重算的 logprob 會跟 rollout 存的差一點點。改完 logprob 往返誤差還是
**1.526e-05**，跟改之前一模一樣 —— 因為兩邊吃的位元相同。

### 34.3 update 放 GPU

20 局 = 14,380 步、minibatch 512：

```

GPU   epochs=4   2.7 秒     （RTX 4060）
```

每個 epoch 快約 5.8 倍。`--device cuda` 只影響主行程的 update ——
`RolloutPool.collect` 送 `state_dict` 之前會 `.cpu()`，worker 一律 CPU。

### 35.2 加一個診斷：explained variance

```
EV = 1 − Var(ret − value) / Var(ret)      model/ppo.py  RolloutBatch.explained_variance
```

`ppo_loss` 回傳的 `value` 是損失，會隨報酬量級變，**不能拿來判斷「學到了沒」**。
EV 可以：接近 0 表示 value head 不比猜平均好，GAE 出來的 advantage 幾乎是報酬
雜訊，policy gradient 在追隨機的東西。

### 35.4 league（`--opponent` 吃逗號分隔的名單）

只打一支會學成專門克它。`VecRollout` 現在吃一串對手，第 i 局配
`opponents[(opp_offset + i) % len]`。

🩸 **`opp_offset` 是必要的。** 只用 `ei % len` 的話，每個 worker 只有 `envs`
個 env（現在是 2），league 再大也只會用到前兩支。主行程傳全域局號進去。

`train.jsonl` 多一欄 `by_opp`（每支各打幾局、贏幾局）—— 只看總勝率的話，
「克死其中一支、其餘全輸」跟「平均進步」長得一樣。
