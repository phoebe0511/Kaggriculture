## 5. 方法論陷阱：送出的訂單 ≠ 成交量

第一次掃 replay 的 `action["market"]` 時，看到頂端玩家 day 15 送出
**259 筆 FERTILIZER SELL**，day 21 送 164 筆、day 25 送 172 筆，整季送出約
1,460 筆，看起來像是主要收入來源。

**是假的。** 交叉驗證 `market.inventory`：FERTILIZER 整季只從 10,000 升到
10,449，也就是雙方合計只成交約 449 個。那些是「有多少賣多少」的訂單，
絕大部分因為 shed 沒貨而中止（`engine-notes.md` §6：錢不夠／shed 滿了 →
該筆訂單中止）。

`tools/revenue.py` 的 docstring 早就寫了這件事。**任何從 `action` 數量推出來
的結論都要用 `market.inventory` 交叉驗證。**

## 7b. ⚠️ 未解：L0 有 6 個測試在 `autocrlf=true` 的機器上一定會失敗

`tests/test_frozen_reference.py` 的 `_sha256()` 直接 hash 檔案原始位元組，
但**期望值是 LF 版的 SHA**（也就是 git 實際存的內容）。

```
git config core.autocrlf                              true
工作目錄 config/opponents/ref-v7.json   2100 bytes，70 個 CRLF
git blob 同一個檔                        2030 bytes，0 個 CRLF

sha(工作目錄位元組)  cfdfc4215d8bc43ba247c65458b796b9435b32c3a1309405b0dbe5731bac566f
sha(LF 正規化後)     25e83d0142559a87faf368faaa0eb51872418ffd0de4f878cf29afb1d6075aba  ← 測試裡寫的
```

`git status` 顯示這些檔**沒有被修改** —— autocrlf 就是這樣運作的。
所以這跟「參數有沒有被改」完全無關，是 checkout 設定造成的。

跑 `pytest` 會看到：

```
FAILED tests/test_frozen_reference.py::test_ref_v2_stays_frozen_at_its_original_params
... ref-v3 / v4 / v5 / v6 / v7 同樣 6 個
```

⚠️ **照 `CLAUDE.md` 的硬規則，不准為了讓它過而改期望值。** 兩條合法的修法：

1. `_sha256()` 改成先做 LF 正規化：
   `hashlib.sha256(path.read_bytes().replace(b"\r\n", b"\n")).hexdigest()`
   行尾不是 JSON 的內容，正規化後仍然抓得到改參數／改縮排／改鍵順序。
   **這條在 2026-08-19 試過並通過（36 passed），但之後被改回原狀，所以現在仍是紅的。**
2. 加 `.gitattributes`：`*.json text eol=lf`，讓 checkout 出來就是 LF。
   從根本解，但要重新 checkout 一次才生效。

**還沒決定用哪條。** 在決定之前，L0 在這台機器上是 30 passed / 6 failed，
不是 36 passed —— 接手的人不要以為是自己改壞的。

## 7c. Phase 2 開工：`contracts.py` 寫好了

schema 定案（`ENCODER_VERSION = 1`）：

```
spatial       [38, 10, 10]   地形 / 作物 / 動物 / unit / 對手盤面
scalar        [66]           現金、時間、人力、種子、shed、市價、市場庫存、商店
```

> 用詞：這份對照表叫 **schema**，版本號是 `ENCODER_VERSION`。
> repo 裡「凍結」另外指 `ref-vN` 那些量尺快照，是兩回事。

### 為什麼是「每個 unit 一個」而不是「每格一個」

實測 60 局：**11.6% 的 unit-turn 是「兩個以上 unit 站同一格、但動作不同」**
（每格 unit 數分布 `{1: 226933, 2: 16709, 3: 1353, 4: 168, 5: 36, 6: 2}`）。

純 per-cell 的 `policy[n_ops, H, W]` 在那 11.6% 上只能給一個答案。但同格的
unit 分得出來 —— 每個 unit 有自己的 inventory，而 `FEED` 是從 unit 自己的
inventory 扣 WHEAT。所以設計成：CNN 整盤跑一次 → 在每個 unit 的格子取出特徵
→ 接上 unit 自己的特徵 → 小 MLP 出 44 個分數。一回合 1 次 CNN + n 次便宜的 head。

### 🩸 兩個靠 replay 驗證抓到的 bug

`legal_unit_mask` 的不變式定成「**寧可放寬，絕不擋掉老師做過的動作**」
（擋掉 = 網路學不到），然後拿 137,673 個 unit-turn 驗：

| 被擋比例 | 原因 |
|---|---|
| **14.66%** | **observation 與 action 錯位一格** —— `steps[t]["action"]` 是在 `steps[t-1]` 決定的，正確配對是 `steps[t].observation → steps[t+1].action` |
| **1.62%** | **`HARVEST` 只允許作物**，漏了動物的 EGG / MILK / WOOL。`engine-notes.md` §1 寫「收成到該 unit 的 inventory」沒限定作物，是我讀漏 |
| 0.12% | 現況。分散在各 op、無單一主因，是老師自己送出的無效動作 |

⚠️ **第一條是今天第二次踩同一個坑**（早上 `agents/replay.py` 也是）。
kaggle-environments 每一格存的是「這個狀態」加上「把狀態推到這裡的那個動作」。
**任何要配對 observation 與 action 的地方都要 +1。**

而且錯位的資料拿去訓練幾乎驗不出來 —— 網路會學到「上一回合的局面配這一回合
的動作」，loss 照樣會降。是那條 mask 不變式把它抓出來的。

### 訓練時不要用 mask 遮 loss

剩下 0.12% 是老師送出的無效動作。訓練時照原標籤學（不遮），
**mask 只在推論時用**。那些動作本來就是引擎的 no-op，不送出去嚴格更好。

**每三次移動就有一次掉頭。** unit 一直在路上，該做的事做不完，田爛掉。

### 根本問題：老師的策略不是 observation 的函數

老師內部決定「unit 3 去澆 (7,2)」，然後連續送 WEST、WEST、NORTH。
**「這個 unit 要去哪」不在任何 observation 欄位裡** —— 那是它的任務指派。

所以只看盤面的策略每回合都在重新猜目標，猜的目標一變就掉頭。
這不是訓練不足，是**資訊本來就不在輸入裡**，加資料或加大網路都不會好。

### 附帶抓到的整合問題

第一版讓 `dynamic_animals` 依商店需求選動物，它選了 **GOOSE**。但老師整季
幾乎不養鵝（`PLACE GOOSE` 在 replay 裡只出現 17 次 = 0.00%），網路不知道
拿鵝要幹嘛 —— 市場買了 16 隻動物，unit 只放進去 3 隻，整季存活 1 隻。

**規則式市場會做出模仿策略沒學過怎麼處理的採購。** 對齊參數（14 建物、
固定 COW 10 + SHEEP 4）之後仍然全敗，但這個機制本身要記住。

### 🩸 教訓：準確率不是有效的 kill switch

我原本設計的 kill switch 是「贏不過 dummy 就是編碼漏資訊」。它**通過了**
（94% vs 16%），但模型是壞的。逐類別召回率也通過了（0.98+）。

真正顯示問題的是**自己打一局、比對動作分布**：MOVE 82% vs 老師 52%、
建物蓋到 24 個（所有頂端隊伍都在 12~15）、方向反轉率 32.9% vs 9.2%。

> **下次的 kill switch 應該是「自己打一局，動作分布跟老師差多少」，
> 不是「在老師的局面上猜得準不準」。** 前者不需要標籤，一局就跑得出來。
