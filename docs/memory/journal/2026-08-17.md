## 0. 兩個基礎問題（比策略重要，先講）

### 0.1 引擎裝的是 1.32.6，但 repo 釘 1.32.7 —— 已修

```
requirements.txt / pyproject.toml / ref-v2,v3,v4 / tests   都寫 1.32.7
實際安裝                                                          1.32.6
```

而且兩版的**價格模型真的不一樣**，不是無害的小改版：

| 商品 | 1.32.6 `below_func` / `below_target` | 1.32.7 |
|---|---|---|
| CARROT | `log` / 0.20 | **`hinge` / 1.00** |
| TOMATO | `linear` / 0.40 | **`hinge` / 0.40** |
| EGG | `linear` / 0.40 | **`hinge` / 0.40** |

1.32.7 新增了 `hinge` 這個 shape（`kaggriculture.py:58-73`）：

```python
HINGE_GAIN = 8.0
if func == "hinge":
    u = x / T
    return u + HINGE_GAIN * max(0.0, u - 1.0) ** 2
```

庫存跌破 `T` 之前是線性、跌破之後二次項接手 —— **缺貨時價格會暴衝**。
`_shape()` 因此多吃一個 `T` 參數，`market_price()` 的四個呼叫點都跟著改。

這條直接影響 `_avg_sell_price()`，也就是 `_plan_basket` / `_plan_animals`
的邊際價值全部建立在它上面。**在 1.32.6 上跑出來的 sweep 結論不能用。**

`pip install kaggle-environments==1.32.7` 升完，diff 只有 2 個 hunk、全部
是上面這段，**沒有覆蓋掉手改內容**（`LAND_ORDER` 仍是 `["NE","SW","SE"]`）。
升級前的檔案備份在 scratchpad（session 結束就沒了，要留自己再存一份）。

> 教訓：`test_engine_version_matches_baseline` 和 `test_engine_rule_fingerprint`
> 就是專門擋這件事的，但**沒人跑測試**（連 `pytest` 都沒裝）。開工先跑 L0。

### 0.2 量尺失效：ref-v2 / ref-v4 已經不等於現行預設

`tests/test_frozen_reference.py` 紅的，原因是上個 session 往
`DEFAULT_PARAMS` 加了東西卻沒切新版 ref：

```
n_structures        6 → 12
oversupply_factor   新增 1.5
crop_oversupply     新增 {"MELON": 4.0}
animal_spend_frac   新增 0.20
```

測試註解寫得很清楚：「新增欄位時這裡**應該**失敗並要求建立 ref-v5；
不可以為了讓測試通過而修改已凍結的 ref」。所以這是設計上的紅燈，不是壞掉。

**後果：現在沒有一把有效的量尺。** `ref-v4` 名義上是「現行預設的展開」，
實際上跟預設差 4 個參數，拿它當對照組量出來的東西意義有限。

還有一個更麻煩的性質，這天才發現：

> **`ref-vN` 只凍結 `params`，不凍結原始碼。**
> 它的 `entry` 是 `agents.gen1:act`，跟被測版本共用同一份 `gen0.py`。
> 所以**改 gen0 的邏輯時，A 和 B 兩邊會同時吃到改動**，`--a gen1 --b ref-v4`
> 量到的只是 params 差異，量不到程式碼差異。

這天就踩了一次：改完 `_house_animals` 之後跑了 80 局 `gen1 vs ref-v4`，
得到 26.2% 以為是大退步，其實那是「gen1 預設 params vs ref-v4 params」，
跟修正無關（`gen1.DEFAULT_PARAMS` 只有 3 個 key，其餘全走 gen0 預設，
而 gen0 預設已經被上個 session 改過了）。

**要量程式碼層級的改動，必須用「同一份原始碼 + 一個開關參數」的兩臂設計。**

## 1. 動物長期閒置的 bug（已修，**尚未驗證**）

### 怎麼發現的

看 `prices_combined_seed0000_gen1_vs_hire-12.png` 的第三格：
**day 1~11 全場只有 1 隻動物**，day 12 才跳到 SHEEP 4、day 13 跳到 COW 6。

去 log 追（`temp/.../logs/seed0000_gen1_vs_hire-12.jsonl`，只看 `player == 0`）：

```
day  1  shed={'COW': 1}  empty_structs={'PASTURE': 1}   ← 倉庫有牛、旁邊有空欄
  ...                                                      連續 11 天完全一樣
day 11  shed={'COW': 1}  empty_structs={'PASTURE': 1}
day 12  animals={'COW': 4, 'SHEEP': 4}                  ← 現金夠買 5 隻牛才解開
```

day 3 hour 8 的任務清單只剩 `{'PLACE': 1}`，**6 個 unit 全部 `PASS`**。

> ⚠️ 一個檔案裡有**兩個 player 的紀錄**（`t` 會重複）。第一次統計沒過濾
> `player` 欄位，crew 分布和每日狀態全部混到對手的，差點得出錯誤結論。

### 根因：兩套邏輯對同一件事用不同依據

| | 依據 | 結論 |
|---|---|---|
| `homeless`（決定要不要 `BUILD`） | **建物種類** —— COW 塞得進 PASTURE | 已有空 PASTURE → 不蓋 |
| `place_want`（決定要不要 `FETCH_ANIMAL`） | **`struct_plan` 的species** —— (3,3) 規劃是 SHEEP | 倉庫沒 SHEEP → 不撿 |

兩邊都認為自己沒事做，於是誰都不動。

probe 證實（monkeypatch `_tasks`，seed 0 對 ref-v4）：

```
day 0  PLACE=[('COW',4,2), ('SHEEP',3,3)]  FETCH=[('COW',1)]  shed={'COW':2}
day 0  PLACE=[('SHEEP',3,3)]               FETCH=[]           shed={'COW':1}  ← 卡住
day 1  PLACE=[('SHEEP',3,3)]               FETCH=[]           shed={'COW':1}
 ...
day 7  PLACE=[('SHEEP',3,3)]               FETCH=[]           shed={'COW':1}
```

day 0 買 2 隻 COW、蓋 2 個 PASTURE，一隻進 (4,2)，第二個 pasture (3,3)
被 plan 標成 SHEEP —— 第二隻 $400 的牛從 **day 0 躺到 day 11**。

### 修法

新增 `_house_animals(tiles, board, struct_plan, held)`（`agents/gen0.py:691`），
回傳 `({(x,y): species}, {species: 沒配到的隻數})`，**`PLACE` / `FETCH` / `BUILD`
三個決定共用同一份配置**。兩輪分配：

1. 規劃species剛好有貨的先配（避免牛先佔掉羊的欄）
2. 剩下的空建物改配「結構相符且手上還有貨」的
3. 都沒貨才維持規劃species，讓 `PLACE` 掛著等買

原則是**手上真的有什麼，優先於 plan 想要什麼**。plan 是「接下來該買哪一種」
的偏好，不該讓已經花錢買回來的動物繼續躺著。

`_tasks` 裡兩處改為讀 `place_target` / `homeless`。

### 效果：只有單局，**沒有統計判定**

seed 0 修正後 day 0 就有 2 隻牛在產，倉庫不再有滯留動物。4 個 seed 快測
（gen1 vs ref-v4）差異極大，判不出來：

```
seed0 +7,110    seed1 -16,238    seed2 +21,943    seed3 +18,605
```

**這項改動的貢獻至今沒有被隔離量測過。** 見「還沒做的事」。

## 2. 草莓佔比：可以拉，但拉了沒有變好

### 問題

先量清楚是什麼在擋草莓（probe `dynamic_basket`，seed 0）：

```
day  9  STRAWBERRY 配 7  ypd=0.19  需求=19.0  demand_cap=150  卡在 cap
day 12  STRAWBERRY 配20  ypd=0.22  需求=25.0  demand_cap=169  卡在 cap
day 15  STRAWBERRY 配20  ypd=0.20  需求=31.0  demand_cap=233  卡在 cap
```

`demand_cap` 是 57~279，**完全沒在擋**。真正卡住它的一直是
`cap = n_tiles × max_crop_share`（40%）這條跟商品無關的比例。

而且規劃是**有落實的**：整季種下 34 次 × 4 個 = 136，實際賣出 138，對得上。
期末市價 $247 = 2.06× base，市場確實還在缺貨。

### 做法與結果

`_plan_basket` 加 `per_share`，`cap` 從單一數字變成 per-crop dict。
新參數叫 `crop_share`，**故意不放進 `DEFAULT_PARAMS`**（放進去就得依
`test_frozen_reference.py` 的規則切一版 ref-v5，而它並沒有效益）。

各 30 seed paired 對 ref-v4，`A = ref-v4` 視角（A 贏 = 該變體較弱）：

| `crop_share.STRAWBERRY` | A 得分率 | 95% CI | 變體現金 | 判定 |
|---|---|---|---|---|
| **0.4（對照）** | 50.0% `28/4/28` | — | 62,646 | **+$0 完全一致** ✅ 旋鈕接線正確 |
| 0.5 | 46.7% | [35%, 59%] | 61,237 | ⚪ 判不出來（−$1,061） |
| 0.6 | 68.3% | [56%, 79%] | 59,778 | ❌ **確實較弱**（−$1,692） |
| 0.7 | 56.7% | [44%, 68%] | 62,308 | ⚪ 判不出來（−$74） |

三個都 ≤ 基準，唯一過顯著的是變差。走勢不單調（−1061 / −1692 / −74），
這種形狀通常是噪音蓋過訊號。

**⚠️ 這批數字是在 1.32.6 上跑的**（升級前），CARROT/TOMATO/EGG 的
`below_func` 不同。結論方向大概不會翻，但要引用的話該重跑。

未驗證的假設：草莓搶走的格子是 WHEAT 的 0.83 ypd，而 WHEAT 的
`above_func = log` 超產幾乎不掉價，所以邊際排序本來就該偏向 WHEAT。

## 3. 順手查到的規則

**TOMATO**（`kaggriculture.py:14`, `774-790`）：

```
seed $50   first_yield_day 8   interval 1   max_yield 4   ongoing True
```
