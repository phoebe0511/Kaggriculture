之後 16 代沒動。

之後候選之間的差距就在那個量級。開跑前就標了這個風險，實際發生。

## 2. 第二輪：seeds 54、holdout 加滿 8 支

```
temp/cma/20260827-164222
--seeds 54 --popsize 14 --workers 10 --sigma0 0.08
--warm-start temp/cma/20260827-130938/gen_0030.pkl
一代 756 局 / 539 秒   跑到第 108 代放 STOP
```

`best_so_far`：−28,324（第 1 代）→ −12,875（6）→ −8,654（68），之後 **39 代沒動**
（sigma 0.0128）。

🩸 **第一輪和第二輪的分數不可比** —— 24 個 seed 和 54 個 seed 量的是不同的東西。
第二輪第 1 代的 −28,324 大致就是「第一輪第 30 代那組參數改用 54 個 seed 重量」。

### 兩個擔心都沒發生

```
變化（正 = 變好）        第10->第100   第60->第100
  train                   +4,222      +1,151
  holdout                 +1,225        -509
  kawashigi                 +964      +1,975
  thomas                  +6,751      +2,623
  tetsuya                 -3,754      -3,240
  utkarsh                 +5,836      +2,846
  peikopon                +5,539      +4,411
  lucien                  +7,035      +1,347
  recursion               +8,714      -1,472

```

第 10 → 100 代 **9 支裡 8 支變好**（只有 tetsuya 退），而且 `gen1`（唯一會反應的）
同向。所以：

- ❌ **不是**「專門吃 ladder-top-a」—— 沒訓練過的 7 支也跟著升
- ❌ **不是**「吃 replay 不會反應」—— `gen1` 會反應，也升

**訓練只打一支對手（`ladder-top-a`）這件事，事後看是可以接受的。** 但那是
holdout 給的事後判斷，不是設計上的保證。

第 60 → 100 代是白跑的：train 只 +1,151，holdout 和 5 支往回走。

### 這一輪改的三件事

| | 為什麼 |
|---|---|
| `--seeds` 24 → 54 | 第一輪的過擬合根因，實測需求 |
| `HOLDOUT_TEAMS` 3 支 → 8 支 + `gen1` | 原本只有 tetsuya/recursion/utkarsh，**看不到對 rating 最高的 kawashigi / thomas 有沒有效**。成本每次 checkpoint 多 100 局 ≈ 55 秒（+2.4%） |
| 新增 `--warm-start` | 借上一輪某一代的最佳解當起點，**covariance 重來、sigma 重設**。舊 covariance 是在雜訊排序下學的，而且正是過擬合的方向 |

## 5. 驗收：改進是真的，但對 replay 的數字灌水八成

seed 2000~2039 ×2（正反手配對），跟 CMA 的 train（0~53）和 holdout
（1000~1039）完全不重疊。

### 對 8 支 ladder replay（**不會反應**）

```
              我方       對手     現金比    勝率     雙方合計
gen1        64,432    111,344     57.9%     3.0%    175,777
cma1-g50    69,247     90,235     76.7%    14.4%    159,482
cma1-g68    69,419     90,510     76.7%    15.2%    159,928

相對 gen1：我方 +4,815    對手 -21,109    合計 -16,295
```

🩸 **現金比的改善有 81% 來自壓低對手，而且雙方合計少了 16,295。**
08-27 §3 量過這個遊戲**不是零和的**（錢從 market 賣出來），所以合計變小代表
在把餅做小。而那 8 支全是開迴路 replay ——
`tools/param_search.py` 的 `OBJECTIVES` 早就標了這個誘因問題。

### 對 `gen1`（**會反應**，= `agents.gen0:act` 走 `DEFAULT_PARAMS`）

```
                    我方      對手     現金比    勝率     雙方合計
gen1 vs gen1      81,641    81,641    100.0%    46.2%    163,282
cma1-g50 vs gen1  94,357    75,750    124.6%    95.0%    170,108   我方 +12,716
cma1-g68 vs gen1  89,671    75,565    118.7%    92.5%    165,236   我方  +8,030

cma1-g50 相對自打：我方 +12,716   對手 -5,891   合計 +6,825
-> 只有 32% 來自壓低對手，而且**餅變大了**
```

### 判讀

| | 壓低對手佔比 | 雙方合計 |
|---|---|---|
| 會反應的對手 | 32% | **+6,825**（變大） |
| 開迴路 replay | 81% | −16,295（變小） |

**兩件事同時成立：**

1. **改進是真的。** 對會反應的對手 +12,716、勝率 95.0%，而且餅變大 ——
   那是多產出來的，不是搶來的。
2. **對 replay 的 57.9% → 76.7% 被灌水了。** 八成來自 replay 買不到東西、
   雇不到人。真人會改買別的，那一段不會轉移。

真實的期望改善介於 **+4,815**（對 replay 我方自己的增量）和 **+12,716**
（對會反應的對手）之間；`3.0% → 14.4%` 的勝率提升應該是高估。

**`cma1-g50` 兩個測試都贏 `cma1-g68`**（+12,716 vs +8,030），加上 CMA 期間
holdout 也比較好 —— 出貨用 g50。

⚠️ `gen1` 自打的勝率是 **46.2% 不是 50%**。同一支 agent 兩邊對打、正反手都跑，
理論上該剛好一半，差 3 局（37/80）。可能是引擎 per-unit lockstep 的先後順序
（`kaggriculture.py:545`）造成的位置偏差，或有平手。**沒查** —— 但它讓上面
所有勝率有約 4pp 的系統性偏移。

## 5b. 打包：`submission/cma1-g50/`

🩸 **`serving/build_submission.py:157` 會 `rmtree` 整個 `dest`**，而
`submission/` 底下有 `e2e-round6/`（打包好的網路版，含 6 MB 權重）。所以
**開子資料夾**，用 `copy_files(dest=REPO_ROOT/"submission"/"cma1-g50")`
從 Python 呼叫（CLI 沒有 `--dest`）。`submission/main.py`、`gen0.py`、
`e2e-round6/` 都沒有被動到。

參數是**內嵌**在打包出來的 `main.py`（`PARAMS = {...}`），不是放一份 JSON
進去。那不是偏好，是硬限制：Kaggle 用
`exec(compile(raw, path, "exec"), {})` 載入，**exec 環境裡沒有 `__file__`**
（`build_submission` 的 docstring），`main.py` 無從知道自己在哪個目錄，
旁邊放 JSON 也開不起來。

🩸 **`PARAMS` 裡一定要有 `_replace_defaults: True`。** 驗收走的是
`eval.runner.build_agent`，它看到 spec 的 `frozen` 會自動補這一項
（`eval/runner.py:135-137`）；submission 不經過那條路。不補的話這 51 項會跟
`gen0.DEFAULT_PARAMS` 合併 —— 今天是 no-op，但之後 gen0 多一個預設 key，
上場的就跟量過的不是同一個 agent。

### 驗收打包有沒有出錯

`config/opponents/cma1-g50-sub.json` 走 **`builtin`** 分支 —— `build_agent`
直接把路徑交給 `env.run`，用 Kaggle 自己的 `exec` + `sys.path.append(exec_dir)`
載入，跟正式上場同一條路。

🩸 `--a submission/cma1-g50/main.py` 那種寫法**會炸** —— `load_spec` 走
`__import__`，找不到同目錄的 `gen0`。一定要用 `builtin` 的 spec。

因為引擎是決定性的，判準可以下得很硬：**打包版對 ladder 的 640 局必須跟
`config/params/cma1-g50.json` 逐位元組相同。**

### 關於 self-play（討論，未實作）

🩸 **08-27 的負面結果不能拿來說 self-play 不行。** 那是兩件不同的事：

```
search 失敗的地方   「在一個盤面上 51 個動作哪個最好」
                    要在 ±4,572 的擺盪裡分辨幾百元 -> 需要 656 次延續
RL 需要的           「幾百萬步平均下來梯度方向對不對」
                    雜訊會被樣本數平均掉
```

真正卡住的是**模擬速度**：

```
引擎純 Python，一局 720 步
規則式   ~1.5 局/秒（10 workers）= 1,080 步/秒
帶網路   gen2_model.act 約 11 ms/步 -> 約 0.3 局/秒 = 216 步/秒
10^8 步 / 216 = 129 小時 ≈ 5.4 天（一次嘗試，不保證成功）
```

`serving/` 的 inference server 架構就是為此準備的（`docs/CLAUDE.md`：self-play
worker 不 import torch、走 queue batch）。但 `docs/CLAUDE.md` 明確寫
「不要建議 PPO from scratch」，而且一次下注 5 天。**先做 §6 的量測再決定。**
