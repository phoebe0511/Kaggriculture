# 分工

---

## 1. 先講一件事：ML 的部分是最小的

兩人都對 ML 不熟，很自然會覺得「模型那條線比較可怕」。**反過來了。**

實際的程式碼量大概是：

| 模組 | 行數（估） | 難度來源 |
|---|---|---|
| 網路定義 + 訓練迴圈 | ~300 | 照抄樣板，改改形狀 |
| 搜尋演算法 | ~250 | 演算法，不是 ML |
| 編碼器 | ~400 | 細心，容易寫錯 |
| **對戰產線（多行程）** | ~600 | **效能、行程管理、GIL** |
| **submission 打包** | ~400 | **numpy 手刻前向、時限控制** |
| 遊戲規則鏡像 | ~500 | 讀原始碼要細 |
| 評估天梯 | ~300 | 統計 |

**大的、難的、會炸的，全部是純軟體工程。**

所以分工的原則不是「誰懂 ML」，是**誰扛得住系統風險**。

---

## 2. 兩條線

| | **A 線 — 基礎建設** | **B 線 — AI 邏輯** |
|---|---|---|
| 負責 | 遊戲規則鏡像、編碼器、對戰產線、inference server、submission 打包 | 第 0 代規則式 AI、網路、訓練、搜尋、評估天梯 |
| 技能 | 多行程、queue、效能調優、序列化 | 演算法、統計、一點 ML |
| 出錯的後果 | **整個專案停擺**（submission 爆掉、產線太慢導致訓練循環餓死） | 這一代模型不夠強，下一代再來 |
| 需要新學的 | 幾乎沒有 | PyTorch 基礎（約 2~3 天） |

### 建議：Phoebe 走 A 線

不是資歷排序，是**失敗成本不對稱**。

A 線幾乎全是你這 25 年在做的事——行程管理、queue、共享記憶體、避開 GIL、效能剖析、二進位格式。**沒有一項是 ML。**

B 線需要新學的東西比較多，但學習曲線很短，而且有評估天梯給明確回饋，做錯了馬上看得出來。

### B 線的暖身清單（Week 1 花 2~3 天）

不用學完整個 ML，只要這幾樣：

```
□ PyTorch 的 tensor 操作（跟 numpy 幾乎一樣）
□ nn.Module 怎麼定義一個網路
□ 訓練迴圈的四行樣板：
     forward → 算 loss → loss.backward() → optimizer.step()
□ Conv2d 的輸入輸出形狀怎麼算
□ 怎麼存/讀 checkpoint
```

**不需要**懂反向傳播的數學、不需要懂各種 optimizer 的差別、不需要讀論文。

## 3. 完整工作清單

### Phase 0 — Day 1~3（兩人一起做）

| ID | 工作 | 誰 | 產出 |
|---|---|---|---|
| **T00** | **讀遊戲引擎原始碼**（各自獨立讀完，再交叉對答案） | 兩人 | 規則筆記，兩人都簽字 |
| T01 | 定義三個介面函式的簽名 | 兩人 | `contracts.py` |
| T02 | repo 骨架、pytest、pre-commit | A | 能跑的空殼 |
| **T03** | **Kaggle 各自報名 + 組隊合併** | 兩人 | ⚠️ 今天做 |

> **T00 為什麼要重複勞動？**
> 一個人讀漏一個係數，整季的模型都建在錯的假設上。這是全專案唯一值得兩人做同一件事的地方。

> 🚨 **T03 是行政地雷**：Kaggle 組隊合併有獨立截止日（通常跟報名同一天），而且**兩人都必須事先各自報名並接受規則**。很多隊伍最後一週才想合併，發現隊友沒報名而作廢。**跟技術無關，但會讓整個專案歸零。**

## 4. 關鍵路徑

```
T00 ──→ T01 ──→ T11 ──→ T14 ──→ T20 ──→ T41 ──→ T60
讀原始碼  定介面   編碼器  對戰產線  笨AI   訓練    迭代
                            ▲
                       瓶頸在這裡
```

**T14 慢，後面全部餓死。** 如果 Week 2 結束時吞吐不達標，B 線就會開始空轉，這時候應該停下來一起處理 T14，而不是繼續往前做。

## 5. 程式碼所有權

> **按檔案切所有權，不要按任務切。**

兩人改同一個 repo，衝突不是出在 git 上，是出在**同一個函式有兩個人在改它的行為**。

```
encoding/        A     ⚠️ 兩邊共用，最危險
harness/         A
serving/         A
main.py          A
agents/          B
model/           B
eval/            B
contracts.py     凍結，兩人都不准單方面改
```

**每個檔案只有一個 owner。別人要動就開 PR 給 owner。**

### 三個衝突熱點

**🔴 `encoding/` 的 channel 順序**
B 訓好的模型綁死在順序上，A 一改全部作廢。只能往後加，不准調換或刪除。

**🔴 `contracts.py`**
要改必須兩人同時在場，並評估對現有所有模型的影響。

**🔴 `main.py`**
只有 A 能改。B 交付的是模型檔 + 一份前向計算的參考實作，由 A 整合。

---

## 6. 兩人組必做的一件事

**共用的評估天梯（T21）。**

凍結 4~6 個固定對手（隨機、貪婪、第 0 代、第 1 代…），任何改動都跑固定種子的對局，輸出勝率 + 信賴區間。

**沒有這個，你們兩個會開始爭論「我這版比較強」而沒有任何裁決依據。**

Week 1 就要有。它比網路架構重要。

---

## 7. 同步節奏

| 頻率 | 內容 |
|---|---|
| **每天 15 分鐘** | 只講兩件事：我卡在哪、我要不要動到你的檔案 |
| **每週一次整合日** | 合併、跑完整天梯、更新 baseline |

**`main` 永遠要是可提交狀態。** 任何時刻 clone 下來都要能產出一個合法的 submission。

這條的實際作用：**Week 5 出事的時候，手上永遠有能交的東西。**
